## 2. 业务逻辑正确性 — Portfolio.ts dailyReturn 单位修复

### 2.1 ✅ 修复是**真的 bug fix**,且向前兼容安全

**文件**: `backend/src/backtest/engine/Portfolio.ts:192-197`

```diff
-          1) *
-          100
+          1)
```

**修前**: `getMetrics().dailyReturn` 返回**百分点** (1% → 1);`resetDailyPnl()` 把这个值 push 进 `this.daily_returns: number[]`,然后:

- `BacktestEngine.calculateSharpeRatio` 把 `daily_returns` 当 decimal 用,`(avgReturn * 252 - 0.03) / (stdDev * sqrt(252))` — risk-free `0.03` 是 decimal,但 returns 是 percent (100x),导致 Sharpe 完全失真 (会比真实值大 ~100 倍)。
- `BacktestEngine.calculateSortinoRatio` 同 bug。
- `BacktestController` 把 `daily_returns` 持久化到 `BacktestResult` 表的 `daily_returns` jsonb 字段。
- `frontend/src/components/backtest/BacktestResults.tsx:238` 又 `ret * 100` 用于折线图 — **double-percent**,显示 100% 实际是 1% 真值。

**修后**: `dailyReturn` 一致为 decimal (1% → 0.01),Sharpe / Sortino 与 0.03 risk-free 单位一致,frontend `ret * 100` 显示正确。

### 2.2 ✅ 影响范围已确认极小

经过 grep:
- `engine/Portfolio.ts` 仅被 `BacktestEngine.ts` + `OrderManager.ts` 引用 (legacy event-driven 路径)。
- 现代 `quant/backtest/internal/QuantBacktestEngine.ts` 是**完全独立**的实现 (有自己的 dailyReturns 计算,不复用 `Portfolio.ts`),不受影响。
- `PortfolioReturnSimulator` (生产 portfolio-simulate 接口) 也完全独立,不复用 `Portfolio.ts`。
- 前端 `Portfolio.tsx` / `portfolioService.ts` 的 `dailyReturn` 字段来自 `PortfolioReturnSimulator`,与 `Portfolio.ts` 无关。
- `engine.getStatus()` (BacktestEngine.ts:551) 暴露的 `portfolioMetrics.dailyReturn` 实际**没有任何 production consumer** (grep `engine.getStatus` 无业务调用)。

**结论**: 改动只影响 legacy `BacktestEngine` → `BacktestController` 这一条路径,其他全部隔离。

旧 `backtest_results.daily_returns` jsonb 列里存的是**百分点值** (修前格式)。本 PR 不做 migration,旧行查看时 frontend 仍会 `*100`,显示 100x 失真。

## 3. QuantWorkflowReadinessService.ts (820 行新增 — 核心)

### 3.1 ⚠️ P1 — service 是**纯 stateless 评分函数**,不读 DB / 不集成现有服务

**文件**: `backend/src/quant/workflow/QuantWorkflowReadinessService.ts`

整个文件**零 import**,纯函数接受 `QuantWorkflowInput` (用户/前端传入快照),返回评分结果。**不读** `BacktestResult` / `PaperTradingPortfolio` / `RiskAlert` 等任何 DB 表,**也不调** `backtestService` / `paperTradingFacade` / `riskGuard`。

grep 验证: `evaluateQuantWorkflowReadiness` / `QuantWorkflowReadinessService` 在 backend/src 内没有任何下游消费者 —— 唯一调用点是 `QuantController.evaluateWorkflowReadiness`,而 controller 又把 `req.body` 原样传给 service。

**这意味着**:
- service 只是"自我评估表单的评分引擎",**没有实际的 backtest/paper-trading 集成**;
- 前端 `WorkflowReadinessTab` 让用户**手填**所有 30+ 字段;
- "applyLatestBacktest" 按钮 (`WorkflowReadinessTab.tsx:179`) 仅从最近完成的 `BacktestTask.run_summary` 抽 6 个字段(trade_count / sharpe / drawdown / excess_return + 写死 validation_split=true),其余靠用户手填;
- canary "通过"标志 `verdict.can_promote_paper_to_canary === true` 也只是评分计算结果,**不是真实 canary gate 接入**;
- `verdict.conclusion` 是文本结论,**不会写回任何状态机**,看完即过。

**风险**: PR body 写的是 "phase 1-3 quant workflow readiness gates",容易被理解成"真的接入了门禁";实际只是 P1 (UI checklist) 的 readiness scoring。如果未来有人误以为"通过了 phase 3 = 真的开 canary 资格",会造假阳性。

**修复建议** (P1, 不阻塞 merge):
- service 文件顶部加 docstring 写清楚 **"this is a stateless self-assessment scorer; it does not query DB or block any real operation"**;
- PR docs `docs/trader-system/37_quant_workflow_readiness.md` 应该明确**这是 phase 1 的引导 UI,不是 enforcement gate**,后续 phase 2 才接 `backtestService` / `paperTradingFacade` 实数据;
- frontend tab 顶部 Alert 加一句 "本页用于评估你已掌握的指标是否达到门禁,不会自动拉取数据库" (现在只写了 "先确认数据和简单策略能跑")。

### 3.3 ⚠️ P2 — 几个评分 edge case

**a. 缺失字段 (NaN) 等同于 0 阻断 — 文档说是 by-design**

`normalizeNumber(undefined)` 返回 `NaN`,然后 `NaN >= ready_min` 永远 `false`,`NaN >= degraded_min` 也永远 `false` → 走 `blocked`。Doc (37_quant_workflow_readiness.md) 写了 "Missing numeric fields are treated as blocked, never as passing values"。

合理,但前端默认表单值很多是 0 不是 undefined (`buildStarterValues` line 624),实际是用 `0 >= ready_min` → blocked,跟 doc 说法一致但跟"未填写"语义不同。无 bug,只是 UX 上"未填"和"填了 0"无区别。

**b. stage 1 评分错位**

`buildStage` line 634: `Math.round((earned / totalWeight) * 100)`。如果所有 check 都 `blocked` 但**没有任何 mandatory 失败**,score=0,落入 `score >= 60 ? 'degraded' : 'blocked'` → blocked。合理。

**c. carryPreviousStageCheck weight 影响下阶段分数**

stage 2 的 `stage_1_ready` weight 10,如果 stage1 blocked 它就 blocked。但 stage2 总分会自动计入 stage1 状态。看起来合理 (不允许跨阶段跳过)。

**d. `degraded` 分支细节**

`verdict.status` = `stage3.status`,但 stage3.status 即使 `degraded` 时,`status_label` 写 "阶段 3 需人工复核",`can_promote_paper_to_canary` = `stage3.status === 'ready'` → 仍正确锁住 canary 仅 ready 才放行。设计无 footgun。

### 3.4 ✅ 无"虚假通过"风险

只要 `mandatory` check 任意失败 → stage = blocked → `can_promote_paper_to_canary = false`。Mandatory 设置覆盖了关键 gate (validation_split / walk_forward / risk_guard_breaches=0 / point_in_time_ready / etc.)。即使 score >= 60 给 degraded,canary 也要 ready 才放,**不存在"degraded 滑过"**。

### 3.5 ✅ 无"过严 block"用户合理操作

只要 input 全填且超过 ready 阈值就 ready。`buildPassingExampleValues` (WorkflowReadinessTab.tsx:660) 给的 demo 值 (98% coverage / 252 天 / 0.51 corr / 0 breaches) 都是合理 production 值,不会刁难真实用户。

## 4. API Route + Controller

### 4.1 ⚠️ P2 — `POST /workflow-readiness/evaluate` 入参**零校验**

**文件**: `backend/src/api/controllers/QuantController.ts:222-230`

```ts
async evaluateWorkflowReadiness(req: AuthenticatedRequest, res: Response) {
  try {
    const data = evaluateQuantWorkflowReadiness(req.body || {});
    res.json({ success: true, data, message: data.verdict.conclusion });
  } catch (error: any) {
    logger.error('评估量化阶段 1-3 readiness 失败:', error);
    res.status(500).json({ success: false, message: error.message });
  }
}
```

`req.body` 原封不动塞进 service,**没有 express-validator 校验**。Service 内部用 `normalizeNumber` / `String(value || '').trim()` 容忍各种 garbage,所以**不会 500 也不会 crash**,只会评分变 blocked。

**风险**:
- 没有 body size 限制,如果有人 POST 100MB JSON 会跑过 multer/body-parser 上限 (express 默认 100KB),但万一调高了会卡 service。
- 没有 strategy.preset_key whitelist,任何字符串都会 fall back 到 default preset,**没有 audit trail**。

**修复建议** (P2):
- 加 `body('strategy.preset_key').optional().isIn(['steady_momentum_basic', 'dividend_defensive_basic', 'reversal_observer_basic'])`;
- 加 `body('data.daily_bar_coverage_pct').optional().isFloat({ min: 0, max: 100 })` 等基础数值范围。

非阻塞 — service 内部容错正确,不构成 P0/P1。

### 4.2 ✅ response shape 稳定,跟前端 contract 一致

后端 `QuantWorkflowReadiness` 接口 (service.ts line 100-117) ↔ 前端 `frontend/src/services/labService.ts:842-861` 完全镜像 (相同字段名 / 相同类型)。test `lab-workflow-readiness-ui.test.ts` 静态扫描前后端的 endpoint / type 匹配。

### 4.3 ✅ 错误处理一致

`evaluateWorkflowReadiness` / `getWorkflowPresets` 都走 `res.status(500).json({ success: false, message })`,跟 `QuantController` 其他方法 (line 17, 39, 75, 144, 154, 167, 177...) 一致 — 没有引入新的 error shape。

### 4.4 ✅ 路由顺序无冲突
