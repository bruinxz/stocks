## Task 2 — nginx 413 (反馈多图)

**根因**: nginx `client_max_body_size 5m`, 前端写"最多 9 张 × 5MB"诱导用户超限,
后端只回 multer LIMIT_FILE_SIZE/COUNT 默认 500, 用户看不到清晰中文错误.

**修了** (这部分能在不 ops sudo 下做的最稳方案):

1. **前端**: `frontend/src/pages/workspace/SystemWorkspace.tsx`
   - "最多 9 张 × 5 MB" → **"最多 3 张 × 1.5 MB"** (总 < 5 MB, nginx 不 413)
   - `beforeUpload` 内加 1.5 MB 单文件 size 检查 + 友好中文提示
   - hint 文案改成 "nginx 限制 5 MB"

2. **后端 middleware**: `backend/src/middlewares/uploadFeedback.ts`
   - `fileSize: 5 MB → 1.5 MB`, `files: 9 → 3`
   - 新增 `uploadFeedbackImages(field)` wrapper: 把 multer 的
     `LIMIT_FILE_SIZE` / `LIMIT_FILE_COUNT` / fileFilter 错误统一翻成 400 + 中文
     ({ message: "单张图片不能超过 1.5 MB" } / "最多上传 3 张图片")
   - 导出 `FEEDBACK_MAX_FILE_BYTES` / `FEEDBACK_MAX_FILE_COUNT` 常量

3. **route**: `backend/src/api/routes/userFeedback.routes.ts`
   - `uploadFeedbackImagesMiddleware.array('images', 9)` →
     `uploadFeedbackImages('images')` (走 wrapper)

> nginx 配置不能在没 ops sudo 时改 — 留 TODO 给 ops 后续 `client_max_body_size 20m`.

## Task 3 — AI 弹窗 mode=off 引导

## Task 4 — TodayWorkspace tab 吃浏览器后退

**根因**: tab 切换只 `setActiveKey(key)`, 没同步到 URL → 用户切 4 个 tab 后,
URL 一直停在初始, 浏览器后退按钮按理直接回上一页 (dashboard);
但若 AlertsBell 跳进来时带 `?tab=...`, useLocation.search 一变就重切.
旧代码"读 query 但不写", 切完 tab 后 URL stale, refresh 又跳回 signals.

**修了**: `frontend/src/pages/workspace/TodayWorkspace.tsx`
- 新 `handleTabChange(key)`: `setActiveKey(key)` + `navigate(?tab=key, { replace: true })`
- `replace: true` 保证 tab 切换**不进 history stack**, 后退键直接回上一页
- refresh 仍保留当前 tab (URL 同步), 不破坏现有 AlertsBell `?tab=` 入参语义

## Task 7 — trade_reason 覆盖率排查

**根因审计**: `paper_trading_trades.trade_reason` 7d 全 NULL, 但代码现状已经
全部 BUY/SELL 入口写 reason:

| 入口 | 文件 / 行 | 状态 |
|---|---|---|
| Facade BUY (手动 / closePosition) | `PaperTradingFacade.ts:1241` | ✅ `facadeResolveTradeReason(options, 'BUY')` |
| Facade SELL (手动 / closePosition / 强平) | `PaperTradingFacade.ts:1389` | ✅ `facadeResolveTradeReason(options, 'SELL')` |
| Automation BUY (autoBuy cron) | `PaperTradingAutomationService.ts:6909` | ✅ `buildTradeReasonFromSignal(signal)` |
| Automation SELL (autoSell cron) | `PaperTradingAutomationService.ts:7055` | ✅ inline build |

trade_reason 提交 commit `6cb3094 feat(AL-3)`, 2026-06-21 部署到 prod.

**最可能原因** (按概率排序):

1. **审计窗口 (7d)** 大头是 6/14-6/20 旧 trade, AL-3 部署前的, 自然 NULL.
2. AL-3 部署后 (2026-06-21 之后) 至今没有新 trade (autoBuy/autoSell cron 没触发或
   被风控全拦).
3. 假设 1+2 都不成立 → 写入路径 bug; 但 grep 显示 4 个 insert 全有 trade_reason
   字段, 不太可能漏.

**下一步排查** (需要 prod SQL 权限, 这里只能列):

```sql
-- 1. 看最近 24h 是否有任何新 trade
SELECT created_at, direction, symbol, trade_reason IS NULL AS reason_null
FROM paper_trading_trades
WHERE created_at > NOW() - INTERVAL '24 hours'
ORDER BY created_at DESC LIMIT 20;

-- 2. 按 24h / 7d / 30d 分时段看 trade_reason 覆盖率
SELECT
  date_trunc('day', created_at) AS d,
  COUNT(*) AS total,
  COUNT(*) FILTER (WHERE trade_reason IS NOT NULL) AS with_reason
FROM paper_trading_trades
WHERE created_at > NOW() - INTERVAL '14 days'
GROUP BY 1 ORDER BY 1;

-- 3. 如果有新 trade 且 trade_reason 仍 NULL → 写入路径 bug, 看具体行的
--    autopilot_decision_id / signal_id 找上游
```

> 当前会话只能 audit 代码静态正确性, prod SQL 验证留给下一轮 (用户 SSH 后跑).
