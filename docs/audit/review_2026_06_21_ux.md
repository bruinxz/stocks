## 二、Findings

### #1 [P1] 用户反馈上传多图必 413 — nginx `client_max_body_size 5m`

**操作触发**：系统介绍 → 用户反馈 tab → 新建反馈 → 拖入 2 张 4MB 截图（或 1 张 6MB 手机原图）→ 点提交。

**用户看到**：`提交失败: request entity too large` 红色 toast（已验证：往 prod `/api/me/feedbacks` POST 20MB 数据返 `HTTP 413` + `{"message":"request entity too large"}`）。

**根因**：
- 前端 `FeedbackTab` 限制每张 ≤ 5MB / 共 9 张（`SystemWorkspace.tsx:331` "最多 9 张，每张 ≤ 5 MB"），让用户以为可上传 45MB
- 后端 multer 同样允许 `fileSize: 5*1024*1024` × `files: 9`（`backend/src/middlewares/uploadFeedback.ts:54-56`）
- **但 nginx `client_max_body_size 5m`**（`scripts/deployment/samples/nginx-stocks.conf:41`）会在 multer 拿到 body 之前就 413。FormData multipart overhead 让"5MB 单图"也很容易超 5m 阈值。

**用户感知**：以为系统坏了，但弹窗 toast 没说 "图片太大"，错误信息 `request entity too large` 不在 STATUS_LABEL 字典里 → 帮助文案 0。用户会重试 → 再失败 → 放弃。

**建议修复**：
- 立即：nginx 这条 location 单独 `client_max_body_size 50m`（与 multer 总额对齐）+ 前端文案改成"单张 ≤ 5MB"（去掉"最多 9 张"误导）
- 长期：前端 `createMyFeedback` 加 client-side total size check，>nginx 阈值时本地拦截给友好提示

### #4 [P1] 拓扑图 backend 渲染数据全用 user_id=4 硬编码 → 多账号场景下展示别人的资产

**操作触发**：任何非 user_id=4 的账号 → 系统介绍 → 架构图 tab → 拓扑卡片"模拟盘"节点。

**用户看到**：节点 stats 里展示的 `current_cash` / `total_value` / `position count` / 最近一笔交易 `symbol/name/direction` 都是 user_id=4 的（即 prod 默认 admin / 主账号）。

**根因**（`backend/src/api/controllers/DataController.ts:195-206`）：

```ts
"SELECT COUNT(*)::int AS n FROM risk_alerts WHERE user_id=4 ..."
'SELECT current_cash, total_value FROM paper_trading_portfolios WHERE user_id=4 LIMIT 1'
'SELECT COUNT(*)::int AS n FROM paper_trading_positions WHERE portfolio_id IN (SELECT id FROM paper_trading_portfolios WHERE user_id=4)'
'SELECT symbol, name, direction, created_at FROM paper_trading_trades WHERE portfolio_id IN ... user_id=4'
```

route 已挂 `authController.authenticate`，但 controller **没读 `req.user.id`**，全 hardcoded 4。

**用户感知 + 隐私问题**：
- 普通用户在拓扑节点 popover 里能看到 admin 账号的现金、持仓数、最近一笔标的+方向（如"600519 SELL"）
- 这是 **轻度数据泄露**：交易方向 + 标的 + 时间戳 = 别人的实盘动作

**建议修复**：把 4 个 SQL 都改为读 `(req as any).user.id`；写一条测试守"user A 的拓扑不返 user B 的 trade"。

### #5 [P2] AI 分析弹窗 v1 fallback layout 把 hold + 置信 0 当 "feature" 显示

**操作触发**：账号设置 → 风险参数 → 分析引擎模式 = off → 任意股票点 AI 分析按钮。

**用户看到**：
- 顶部综合建议变成 warning Alert（黄色），写着 "综合建议: 未知"（`reco === 'unknown'`，`AIStockAnalysisModal.tsx:243-244`）
- 各维度核心要点全部"（暂无信息）"（`points.length === 0` 走 fallback，line 292）
- 没有任何提示"分析引擎被你关了"或"请去 settings 打开 shadow 模式"
- 用户看到"综合建议: 未知" + 一堆"暂无信息"会直觉理解成"系统坏了"，而不是"我没开"

**根因**：`AnalysisEngineService.analyzeStock` 在 mode=off 时返结果是 v1 形态（没有 `metadata.engine_variant='multi_dim_v1'`），`isV2Result` 返 false → 走 v1 layout。v1 layout 没有针对"off 状态"的友好引导。

**建议修复**：
- `AIStockAnalysisModal` 顶部加 Alert：当 `result.dimensions.length > 0 && all key_points 为空 && status==='completed'` → 提示"分析引擎处于 off / shadow，无 hard 数据。请去 [账号设置 → 分析引擎] 打开 shadow 收集证据"
- 或后端在 mode=off 时直接返 `status='disabled'`，前端单独走"功能未启用"卡

### #6 [P2] AlertsBell `?tab=risk_center` 跳转后，浏览器后退会引起再次 setActiveKey

**操作触发**：用户从其他 workspace 跳过来 → 点 Bell → 跳 `/workspace/today?tab=risk_center` → 用户点击其他 tab（如"今日信号"）→ 浏览器后退键。

**用户看到**：浏览器 URL 是 `?tab=risk_center` → `useEffect([location.search])` 触发 → 又被切回 risk_center。即用户手动切了 tab 后浏览器后退就回不到"上一个 tab"，要回到 signals tab 必须再点一次。

**根因**（`TodayWorkspace.tsx:174-180`）：`useEffect` 监听 `location.search`，每次 search 变化都强制 `setActiveKey(query.tab)`。注释里写"之后用户切 tab 不再被 query 覆盖"，但实际**用户手动切 tab 时 `location.search` 没变，没问题**；问题在浏览器后退：URL 退回时 `location.search` 又变成 `?tab=risk_center`，useEffect 又跑一次。

**用户感知**：后退按钮 "失灵"。中度疑惑，不会写飞书反馈，但会留 paper cut。

**建议修复**：用 `useRef` 记 "applied 过的 search"，避免 same-search 重复 apply；或用 `react-router` 的 `useSearchParams` + 主动 `setSearchParams` 清掉 query。

### #7 [P3] WebSocket `/ws/alerts` prod 不可达 → AlertsBell 永久 polling 模式

**用户感知**：Bell tooltip 末尾会显示 `(轮询)` 而非 `(实时)`。新告警有 30s 延迟，critical 告警延迟弹窗。功能没坏但 SLA 与设计不符。

**验证**：
- prod nginx sample `nginx-stocks.conf` 的 `location /api/` 块有 `proxy_set_header Upgrade $http_upgrade` ✓
- 但 **没有 `/ws/` 专属 location**。WebSocket URL `wss://host/ws/alerts?token=...` 走的是 SPA fallback `location /` → 转 `127.0.0.1:3001`（前端 pm2 serve），不是 backend 3000
- 即生产环境 ws 连接落到了前端静态服务器，立即 close → 触发 `useAlertsRealtime` 的 backoff 重连，6 次后 give up → 永久 polling

**根因**：nginx 配置遗漏 `/ws/alerts` 路由到 backend 3000 + `proxy_http_version 1.1` + Upgrade header。

**建议修复**：在 `nginx-stocks.conf` 加：

```nginx
location /ws/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 300s;
}
```

- **Login 死循环防线** (Batch AK)：`api.ts` 的 `sessionRedirectingToLogin` module-level singleton 真生效。`AppContent` 的 catch 分支真的清了 token + user state。

## 五、Methodology Note
