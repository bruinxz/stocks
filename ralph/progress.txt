## Codebase Patterns

### Frontend
- **Frontend workspace shells live under** `frontend/src/pages/workspace/`. Each is lazy-loaded in `frontend/src/App.tsx`. When adding workspace tabs in later stories, edit the shell file in place — do NOT introduce parallel page files.
- **All 6 workspace shells use `WorkspaceLayout`** (`frontend/src/components/layout/WorkspaceLayout.tsx`). When a future story adds real content for a workspace, render the new tab UI as `children` (or branch on `activeKey`) and leave the KPI strip / side rail handled by the layout — do NOT rebuild the chrome from scratch.
- **WorkspaceLayout props contract:** `tabs[]` (each `{key,label,icon?}`) → 220px left rail; `kpiSlot` → centered metrics inside the 96px KPI bar; `headerActions` → right-aligned `Space`; `activeKey` / `onTabChange` are required to drive the side-rail selection.
- **App.tsx single source of truth** for routes and the top-level menu. The `routeSelectionAliases` array maps legacy paths to the workspace whose sidebar entry should be highlighted; the `<Routes>` block defines the actual `<Navigate>` redirects. Whenever a legacy path is deprecated, update BOTH arrays.
- **Legacy page imports** are kept (under `/legacy/*` routes) so deep links and embedded iframes still resolve. Only physically delete a page file after all six workspaces have absorbed its functionality (stories US-015..US-018).
- **Workspace shell CSS lives at the bottom of `frontend/src/index.css`** under a `Workspace shell (US-002)` banner. The shell uses `.workspace-shell`, `.workspace-kpi-bar__inner`, `.workspace-side-tabs`. Media query at 1024px stacks the side rail above content.

### A-share data ingestion (US-005+)
- **New data sources live in 3 paired files**: `backend/src/models/<Source>.ts` (Sequelize model, register in `models/index.ts` AND `config/database.ts`), `backend/src/data/sources/<Source>Client.ts` (Python helper wrapper), `backend/src/data/services/<Source>SyncService.ts` (DB write + range/checkpoint). Add a CLI under `backend/src/scripts/sync-<source>.ts` and a `sync:<source>` npm script. The northbound trio is the canonical reference.
- **AKShare Python commands live in `backend/python/akshare_helper.py`**. Add a new function + a dispatcher case in `main()`. Always (1) accept both `YYYY-MM-DD` and `YYYYMMDD` and convert internally, (2) build a柔性 col_map (Chinese column headers drift between akshare versions), (3) include the full original row as `raw_payload` for audit, (4) return `[]` (not raise) on empty data so the TS layer can checkpoint a "tried but empty" day separately from a hard failure.
- **Idempotent reruns = composite-PK + `bulkCreate` + `updateOnDuplicate`**. Always include `updated_at` in `updateOnDuplicate` so ops can see refresh times. Default `syncRange` to skip-existing for cheap catch-up; expose `--force` for backfills.
- **Multi-record-per-stock (US-006 龙虎榜) ⇒ N-tuple PK**: when one stock spawns many rows per day (e.g. `buyer_seat × seller_seat`), the model PK is a 3-/4-tuple. Do the cartesian fan-out IN the Python helper so the TS service stays a clean `bulkCreate`. Keep both halves in `raw_payload` (`{list_row, buyer_row, seller_row}`) for audit.
- **Business-logic tagging (e.g. `is_famous_yz`) belongs in the TS service**, NOT the Python helper. Python is the dumb fetcher; TS owns whitelists like `backend/src/constants/famousSeats.ts` so the rule can evolve without re-running Python.
- **Cross-day derived fields (e.g. `continuous_days` 连板天数) belong in the TS service** — `LimitUpSyncService.syncDate` looks back 5 calendar days of LimitUpStock history before each `bulkCreate` and recomputes `CD = yesterday.CD + 1` (max with akshare's own value as a floor). Pattern for any field that depends on previous-day records: `loadRecentHistory()` → map override → bulkCreate.
- **Multi-endpoint merge (US-007 涨停 zt_pool + strong_pool)**: when AKShare has two endpoints with overlapping rows + each-side-unique extras, pick one as primary (zt_pool), index the other by stock_code as a side-car dict in Python, then 1-pass merge in `_, row in df_primary.iterrows()` + emit secondary-only rows in a final loop using a `seen_codes: set` guard. Keep both raw rows in `raw_payload = {primary_row, secondary_row}`.
- **AKShare time-of-day strings are inconsistent** (`"09:25:03"` or `"92503"`). Parse digits-only in the Python helper (`_is_one_word(limit_up_time, open_times)` in `akshare_helper.py`) — let TS consumers see a pre-computed boolean instead of re-parsing. Counterpart for `is_famous_yz`/whitelists is in TS — divider: per-row computation that's pure data goes Python-side; rules that may evolve or need DB joins stay TS-side.
- **Helper micro-functions to copy across AKShare commands**: `_cell_str / _cell_float / _cell_int / _row_to_jsonable / _format_iso_date` in `akshare_helper.py` — defined once for US-007, reuse them in future commands (`get_industry_flow`, `get_earnings_forecast`, etc.) instead of repeating `safe_float_value(row.get(col)) if col else None`.
- **Multi-endpoint join WITHOUT a shared key (US-008 行业资金流)**: `stock_sector_fund_flow_rank` has metrics but no board code; `stock_board_industry_name_em` has the code but joins by Chinese 板块名称. Indexing the smaller "name→code+metadata" df into a Python dict, joining per row, and emitting `industry_code = "FALLBACK-<name>"` for unmapped names keeps rankings intact. **Cross-DB joins (e.g. `limit_up_count` requires JOIN-ing LimitUpStock by industry name) belong in the TS service, not Python** — same divider as `is_famous_yz` and `continuous_days`.
- **Real-time-only snapshots (US-008 fund_flow / name / cons family)**: a subset of AKShare endpoints CANNOT replay history; you only get "now". The `date` param becomes a `trade_date` LABEL stamped onto each output row by Python — the data is still today's. Document this on the client jsdoc + service jsdoc; don't pretend `--start=2023-01-01` does what it appears to. Schedule once per day post-close; the `INDUSTRY_FLOW_TIMEOUT_MS` default is 240s because per-board `cons_em` fetches dominate (~86 boards × AKShare rate-limit).

### Quant factor infrastructure (US-009+)
- **Factor module tree** lives at `backend/src/quant/factors/` and is the **only** place where factor logic exists: `types.ts` (Factor interface + FactorContext), `FactorRegistry.ts` (singleton — same dedupe-on-register pattern as StrategyRegistry), `FactorPipeline.ts` (cross-sectional batch processor), `normalization.ts` (winsorize/zscore/percentileRanks — **cross-sectional** helpers, NOT to be confused with quant/engine/QuantMath.ts which is time-series). `library/index.ts` is the import-time aggregator: each factor file self-registers via `factorRegistry.register(...)` and gets pulled in by `library/index.ts` so callers only need `import '../quant/factors/library'` once.
- **Factor design contract**: factors output **un-normalized** raw_value Map<stock_code, number|null>. The Pipeline does winsorize(1%-99%) → zscore → percentileRanks across the cross-section. Factors that self-normalize would break cross-factor comparability — **never** call zscore() inside a Factor.compute().
- **Sparse Map is fine**: if a factor can't compute a value for a stock (missing data), just don't include it in the Map. The Pipeline fills the universe gap with a "neutral row" (raw_value=null, z_score=0, percentile=0.5) so factor_scores always has `universe_size` rows per (date, factor) — makes multi-factor JOIN-free.
- **stock_code is suffix-less**: FactorScore.stock_code matches NorthboundHolding/LimitUpStock/IndustryFlow ("600519", not "600519.SH"). When a Factor.compute() reads Stock/DailyBar (which use "600519.SH"), it MUST `symbol.split('.')[0]` before keying the output Map.
- **Pipeline serial-by-factor, not Promise.all parallel**: one bad factor doesn't kill the batch; logs stay readable; debug is straightforward. The compute step within one factor can still batch DB queries internally.
- **library/_helpers.ts** (US-010) is the **library-internal** shared utility module — prefix `_` = "only library code should import this; not exposed via quant/factors/index.ts". Provides `stripSuffix(symbol)`, `inferStockSymbol(code)` (reverse: "600519" → "600519.SH"), `loadStocksByCodes(codes, attrs)` (one-shot batch query that returns Map<stock_code, Stock>), `isFiniteNumber(v)`, `lookbackStartDate(asOf, days)`. Use these in every new factor — don't inline the 5-line symbol-mapping logic 8 times.
- **3 query-shape patterns** to copy when adding a new factor (US-010 codified them):
  - **"Time-series aggregate" (quality/growth)**: pull `factor_date ∈ [as_of - N天, as_of]` from a `symbol`-keyed source table, group by symbol in-memory, then stripSuffix → output.
  - **"Time-series + cross-section" (momentum/low_vol)**: `loadStocksByCodes(universe)` first to get `Stock.id`, then `Op.in: stock_ids` + time range on DailyBar; group by stock_id, `arr.sort((a,b)=>a.time-b.time)`, count back from tail to align on T-N.
  - **"Suffixless-table direct" (northbound/dragon_tiger)**: `Op.in: ctx.universe` + trade_date window — stock_code field IS the output key, no Stock lookup needed.
- **Z-score-friendly raw_value shapes** (US-010 lessons):
  - For "event count" factors (dragon_tiger), use **distinct DAYS** not raw rows — cartesian fan-out in source tables inflates counts unpredictably.
  - Don't write `0` when "未触发" — leave the stock out of the Map so Pipeline's middle-rank neutral default (percentile=0.5) applies; writing 0 collapses the cross-section to a "0 vs positive" bimodal distribution that breaks z-score interpretability.
  - For "lower-is-better" factors (low_vol), return `-stddev` not `1/stddev`: avoid div-by-near-zero noise.
  - For "ratio family" factors (value), use `1/PE + 1/PB` not `-PE - PB`: keeps both ingredients dimensionless and naturally bounded.

### Learnings for future iterations
- **龙虎榜 is a 2-API combo, not 1.** `stock_lhb_detail_em` only gives the day's stock list + reason — you MUST fan out to `stock_lhb_stock_detail_em(symbol, date, flag='买入'/'卖出')` twice per stock to get the seat list. The Python helper does this entirely server-side so the TS layer stays declarative.
- **AKShare positional-vs-keyword signature drift is real.** Wrap `ak.stock_lhb_detail_em(start_date=..., end_date=...)` in `try/except TypeError` + positional fallback. Same for `stock_lhb_stock_detail_em`. This saved a 30-minute debug when an older version was installed locally.
- **Composite PK = (date, stock, buyer, seller).** A single LHB stock has ~10 buyers × ~10 sellers = 100 rows; the cartesian shape matters because (a) buyer席位净额 / 卖方席位净额 isn't decomposable per-pair, and (b) it lets short-term strategies join freely without secondary tables. - **knowing 游资 ≠ free text matching.** 营业部 names are LONG (`"东方财富证券股份有限公司拉萨团结路第二营业部"` = 23 字符) and AKShare occasionally returns 简写. Maintain (a) a 标准全称 whitelist, (b) an alias map for known 简写, (c) a fuzzy 拉萨系兜底 (`东方财富证券` + `拉萨` always counts) — the three-layer match catches > 95% in practice.
- **`canonicalSeatName` is critical for group-by sanity.** Without it, "中国银河证券绍兴营业部" and "中国银河证券股份有限公司绍兴营业部" would be two different keys in any aggregate over `buyer_seat`. Always normalise BEFORE writing — back-filling normalisations after the fact is painful.
- **The `is_famous_yz` boolean is intentionally minimalist** — boolean instead of `famous_yz_name` (e.g. "赵老哥"). One seat may host multiple traders over time; binding a name into the row would force re-tagging on every regime change. Strategies that need the named alias should JOIN against `constants/famousSeats.ts` at query time.
- **180s timeout was chosen empirically.** ~50 LHB stocks/day × 2 API calls + AKShare's 30s+ rate-limit can push a single-day fetch past 60s. Don't drop below 120s without testing on a real busy day (e.g. 政策性新闻日 = 100+ LHB stocks).
- **`raw_payload.{list_row, buyer_row, seller_row}` recovers everything** if AKShare adds a new column we forgot to map (`持股集中度变化` etc.). When extending the model with a derived field, read from `raw_payload` rather than re-fetching.

### Learnings for future iterations
- **AKShare 不是所有端点都能放回历史**。`stock_sector_fund_flow_rank` / `stock_board_industry_name_em` / `stock_board_industry_cons_em` 都是"当下时刻"的实时快照，没有 date 参数（甚至没有任何时间参数）。CLI 的 `--date` 只是 `trade_date` 标签——历史日期回填会让今日数据被打成历史日期的标签，污染数据库。这是数据源限制，不在服务层隐藏；jsdoc + CLI + service comment 三处都明确写。
- **3 个端点的隐式 join key 是 Chinese 字符串**。`stock_sector_fund_flow_rank` 给 "名称"（无代码），`stock_board_industry_name_em` 给 "板块名称 ↔ 板块代码 BKxxxx" 映射。两者都来自东财，名字基本一致；少量边角情况通过 `industry_code = "FALLBACK-<name>"` 兜底，绝不丢行。
- **86 个行业 × 1 次 cons fetch = 86 次外部请求**，AKShare 限速下单日同步耗时 120-180s。timeout 一定要 ≥ 240s，60s 必超。
- **一字板启发式 = 涨跌幅 ≥ 9.95% 且 振幅 ≤ 0.5%**。振幅缺失时只要涨幅触顶就保守视为一字板（跳过选龙头）。全行业全是一字板时（极端情绪日，比如政策性新闻），退而求其次取涨幅最大行——不能让 `leader_stock_code` 永远是 null。
- **`limit_up_count` 是跨 DB join 字段**：industry_flows 表的填充依赖 limit_up_stocks 表的当日数据，所以 sync 顺序应当是先 `sync:limit-up` 后 `sync:industry-flow`（cron 配置时注意）。若两者并发跑，第一次结果会 limit_up_count=0；下一次 sync 同日时 `updateOnDuplicate` 会修正。这层 ordering 关系在 README 的 cron 一节应该 follow up 加。
- **`industries_with_limit_ups / industries_with_leader` 是 ops 指标**，不仅服务 caller 也服务监控：正常交易日应当 with_leader ≈ 86（绝大多数行业能找到非一字板龙头），with_limit_ups 在牛市能到 60-80、震荡市 5-20、跌市 0-5。某天突然 with_leader=0 就意味着 AKShare 抓数大概率出问题，应触发告警。
- **3 个新的 Codebase Patterns 提炼**：(1) 多端点无共享键 join 用 Chinese name 隐式连接 + FALLBACK 行兜底，(2) 跨 DB join 永远留 TS 服务，(3) 实时快照端点要写明 "date 是标签而非过滤器"。这些会被 US-022 高分红低 PE / US-090 股东增减持 等后续股票/财务接口直接复用。
- **Worktree gotcha (still active)**：before `git add`, `rm backend/node_modules`（symlink 污染 git status）。

### Learnings for future iterations
- **3 元组主键 (trade_date, stock_code, factor_name) 是设计核心**。曾考虑用 auto-increment id +
  唯一索引——但 bulkCreate + updateOnDuplicate 对 composite PK 直接支持，省一个 unique constraint
  + 让 "重跑覆盖" 行为最直观。
- **"中性行" 补全是无声的契约**：调用方查 factor_scores 时不需要 LEFT JOIN 处理缺失股票，
  因为每天每因子都保证写满整 universe。raw_value=null + z_score=0 + percentile=0.5 让多因子
  合成 `SUM(z_score * weight)` 自然给缺值股票打 "中性总分"，不会因为单因子缺值就把整只股票剔出。
  US-011 多因子策略可以直接 `WHERE trade_date=? GROUP BY stock_code` 不用关心覆盖率。
- **横截面 vs 时序 normalization 必须分目录**。`quant/engine/QuantMath.ts` 的 mean/stddev 是
  "对一只股票时间序列上的滚动均值/方差"；这里的 mean/stddev 是 "对一组股票同一时点截面值的均值/方差"。
  混用会语义错。命名空间各自独立比 "复用代码" 重要。
- **`Factor.compute` 不写库** 是关键的隔离设计：可以单独跑一个因子拿到 Map 做 debug / 单元
  测试，不需要 DB up；Pipeline 是唯一持久化点，逻辑集中。"compute → persist 分离" 让
  IC 报告 (US-041)、因子热力图 (US-074) 等下游能复用 compute() 输出而不重新写库。
- **Stock.symbol vs FactorScore.stock_code 的格式差异是 US-010 第一坑**：
  老的 Stock / DailyBar / StockValuationFactor 用 "600519.SH" 形式；新的 NorthboundHolding /
  LimitUpStock / IndustryFlow / FactorScore 用 "600519"。在 CLAUDE.md 里写了 `stripSuffix`
  模板代码 + 单元素工具函数，避免 US-010 8 个因子各写 8 次相同的 split。
- **FactorRegistry 全局单例 + 单元测试用 new FactorRegistry() 实例隔离** 是关键模式。
  生产代码（CLI / Pipeline / Strategy）共享单例确保所有因子在一个地方；测试创建独立 registry
  注入到 `new FactorPipeline(registry)` 完全隔离，避免测试间状态污染。`_clearForTesting`
  是 fallback 但鼓励 new instance 模式。
- **CLI 的 `--skip` 与 `--factors` 并存**：白名单 + 黑名单同时支持。--factors 选定一组要跑
  的因子，--skip 在那一组里再过滤。生产场景：cron 跑全部因子 + 黑名单临时下线某个失效因子，
  比改全量列表更安全（一目了然，错过下线就是一次性的）。
- **FactorPipeline 串行调度 vs 并行**：选了串行。8 因子 × 全 A 股 (~5000 只) × ~250 日 lookback
  在 Postgres 上单因子 ~2-3s；串行 8 个 ~20-30s，完全可接受。并行的隐性风险大：
  (1) bulkCreate 同时打满连接池；(2) 日志交错难调试；(3) 单因子 OOM 影响别的。
  改并行的触发条件应当是 "因子数 > 20 且单因子 < 1s" 时再说。
- **`is_active != false` 用 Op.or [{is_active: true}, {is_active: null}]** 是为了兼容
  旧数据（Stock 表里可能有 NULL 的 is_active 字段）。`{is_active: { [Op.ne]: false }}` 看起来更直接
  但 Sequelize 对 `Op.ne` + NULL 的 SQL 行为依赖 NOT NULL 假设，安全起见用 Or 显式。
- **Worktree gotcha (still active)**：before `git add`, `rm backend/node_modules`。

### Learnings for future iterations
- **dragon_tiger 因子的 "天数 ≠ 笔数" 决策**：龙虎榜在 DragonTigerBoard 表里是
  `(buyer_seat × seller_seat)` 笛卡尔展开，一只股票一天可能有 5-10 个 famous_yz=true
  的行。`count(笔数)` 让一天爆量游资 vs 持续多天小量游资的票完全不可比；改用
  `count(distinct trade_date)` 让 raw_value 自然在 0..20 之间，横截面 zscore
  收敛漂亮。
- **dragon_tiger 因子的 "缺失 ≠ 0" 决策**：窗口内一个 famous_yz 都没有的股票
  不入 Map，让 Pipeline 中性补全（percentile=0.5）。强行写 0 会让大多数股票
  挤在 raw=0，把横截面均值拖向 0、zscore 分布退化成 "0 vs 正" 二元。"未上榜"
  与 "上榜但被卖" 是不同的事件，前者保持中性才正确。
- **low_vol 用 `-stddev` 而非 `1/stddev`**：避免分母趋零（停牌全程没动）导致数值爆炸；
  取负号让 Pipeline 横截面 zscore 后高分自然代表低波动股，不需要在 strategy
  层颠倒符号。同样的 "符号选择" 思路也适用于 US-029 之后的高阶因子（如换手率
  双向异常打分）。
- **value 用 `1/PE + 1/PB` 而非 `-PE - PB`**：分母倒数自然无量纲，两个比率都
  在 0..1 区间（除非极便宜的烟蒂股），等权相加不会让 PE=100 完全淹没 PB=2；
  反过来 `-PE - PB` 会让 PE 单一信号主导。
- **momentum 用 `close[T-20]/close[T-120] - 1` 而非 log return**：A 股极端值
  比海外多，对数收益会让极端涨幅更"重"；用比值差 + Pipeline 1%-99% winsorize
  组合反而稳定。120-20 这个 "skip recent 20 days" 设计是经典学术因子（Jegadeesh &
  Titman 1993 + 后续 follow-up）——A 股短期反转特别强，剔除最近 20 日效果显著。
- **`loadStocksByCodes` 的设计权衡**：4 个因子（momentum/low_vol/value 间接/money_flow）
  都需要 universe→Stock 反查；如果每个因子各自 `Stock.findAll({where:{symbol:{[Op.in]:...}}})`
  就是 4 份几乎相同的代码。抽到 `_helpers.ts` 后单点优化（attributes 投影、是否需要 `raw:true`
  等）一次性生效。但**没有把所有数据访问都抽成 DAO**：因子查询 shape 异质性大
  （momentum 要 time-series stock_id JOIN、quality 要 symbol GROUP BY），强行抽
  会让接口爆炸。只抽 "8 个因子里 ≥3 个都用" 的部分。
- **横截面 z-score 友好的 raw_value 形态是 US-010 最大的设计教训**：写完所有 8 个
  因子后回头看，每个都有一个 "怎么把现实信号编码成横截面良性分布" 的小决策。
  CLAUDE.md 把这 4 条（"独立日数 vs 笔数"、"缺失 vs 0"、"-x vs 1/x"、"1/a + 1/b vs -a - b"）
  落在 "横截面 z-score 友好的 raw_value 形态" 一节，US-029+ 加新因子时直接对照。
- **MomentumFactor / LowVolFactor 用尾部计数而非日历对齐**：用 `arr.length - 1 - 20`
  而不是按 `as_of - 20 个日历日` 查询。原因：A 股节假日（春节 7 天、五一 5 天等）
  让 "20 个日历日前" 与 "20 个交易日前" 经常差 5-10 天；尾部计数永远是 "我有的最近 N 个交易日"
  而不是 "日历上 N 天前应该有的"。`QUERY_CALENDAR_DAYS = 220` 足以覆盖 120 个交易日
  + 春节假期 + 一些缺数据缓冲。
- **新因子文件**：要复用 `_helpers.ts` 的 5 个 primitive，**不要**inline 5 行
  `if (!symbol) return ''; const i = symbol.indexOf('.'); return i < 0 ? symbol : symbol.slice(0, i);`
  ——库内已经有 `stripSuffix(symbol)`，统一了 8 份不一致的边界处理。
