- "schema 先行" 模板 (US-025 ANN-001 + 未来 KOL-XXX / 任何"先打基础列让后续 story 填"类): 一个 story 只加 schema 字段 + migration + 默认值 + normalize* helper, 不写实际抽取逻辑 — 实际逻辑由后续 story 各自一个 pure function 填; 本 story 必须做 9 件事漏一不可: (1) **migration up + down 双 SQL** 同时落 (rollback 同名 `-rollback.sql` 与 up 一一对应; 命名 `YYYY-MM-DD-<feature>.sql`); (2) up 用 `ADD COLUMN IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS` 让重复跑幂等, down 用 `DROP COLUMN IF EXISTS` + `DROP INDEX IF EXISTS`; (3) 字段默认值必须配合"未跑过对应 helper 时的安全状态" — priority 必须 'low' 而非 NULL/'critical' (低优先级永远是 fail-safe, 否则历史回填行触发 push 风暴); 'NULL = 未跑过' vs '默认占位枚举 = 跑过但识别不出' 的语义边界要写到 model + helper 注释里; (4) Sequelize Model `@Column` 三件套 (type/allowNull/defaultValue) + indexes array 显式 name (与 SQL 的 `CREATE INDEX <name>` 字面量一致, 不能让 Sequelize auto-generate, 否则 ORM 和 migration 漂); (5) Record/DTO interface 加新字段 + ts 类型用 export 的 enum (`AnnouncementPriority = (typeof ANNOUNCEMENT_PRIORITY_VALUES)[number]`) 让后续 helper 强类型守; (6) **3 个 normalize* 函数** (priority/eventType/entities) 接受 unknown 兜底 — 处理远端 AI 返垃圾 + caller 传错 + 中英文别名 + null/empty 边界, **默认值必须是安全态而非 escalation 态**; (7) builder 函数 (heuristic + payload 两路) 都填新字段, payload FAILED 分支用 normalize* 默认值 (不调 normalize, 避免远端 AI 把 priority='critical' 借 FAILED 路径泄漏); (8) DataSource.saveSummaries 的 `bulkCreate` map + `updateOnDuplicate` array 同时含新列 — 漏 updateOnDuplicate 让 re-sync 同标题漂回默认值, 是这类 story 最容易忽略的隐性 bug; (9) META-GUARD 3 件套 fs+regex 守 model 含 declare + index name + saveSummaries 含字段 + updateOnDuplicate 含字段 + migration up/down 形态全 — 缺一让后续 ANN-002~007 实现时漏改任一处都看不出. 与 US-018/019 抽 helper 后切干净的反向 guard 同款思想, 但本 story 是"先建桩位再让后续填", 反向 guard 不适用 — 改成"前向 guard"守新列已声明 + bulkCreate 已包含. 真 PG 可达时建议在 CI 之外手跑一次 migration up + down (临时表 sandbox), psql `\d+ table` 看 default/comment/index 是否如预期 — IF NOT EXISTS 让本地能反复试不破坏. 命名约定: `idx_<table>_<col1>_<col2>` 顺序按查询 WHERE 优先级 (priority/announce_date DESC 让 "今日 critical" 用得上).
- "短词字典扫长字符串 + 实体抽取" 模板 (US-026 classifyEventType / US-027 extractEntities 系列, 未来 KOL/ANN 任何"从文本里识别实体/事件"启发式): 4 件套必备 — (1) **字典顺序按 "具体度从高到低" 排** — 同 keyword 优先匹配更具体的 (e.g. '控股股东' 必须在 '股东' 前, '解除质押' 必须在 '质押' 前, 否则字面相反的语义被泛化词抢走); 字典 ordering 必须显式单测 (assertion: indexOf(具体) < indexOf(泛化)), 不能依赖人脑 review. (2) **子串覆盖 (overlap) 判断** — 当多个 keyword 可能匹配同一锚点 (e.g. '控股股东' 命中后 '股东' 子串落在窗口内), 用 `out._idx + role.length` 范围判断, 重叠则跳过, 不重叠则继续. **多锚点重复角色** (e.g. '控股股东及 5% 以上股东') 必须用 `text.indexOf(role, searchFrom)` 循环找下一个非重叠锚点, 简单 indexOf 取首个会丢第二个独立锚点. (3) **placeholder 设计 vs 真姓名抽取** — 中文短文本里用正则切真姓名召回率 < 60% (动词 '变更'/'拟减持', 普通名词 '大会'/'公告' 全是 2-3 字中文, 无法区分), 启发式只输出 `name=role placeholder` (与 normalizeEntities 契约自洽), 真姓名留给远端 AI 透传. 与 placeholder 同款思想适用 "从 60 字以内文本抽具名实体" 的所有场景 — 召回率 < 70% 时直接放弃正则方案, 用 placeholder + AI 兜底, 别勉强. (4) **roundtrip guard** — extractXxx 输出必须满足 `normalizeXxx(extractXxx(t)).length === extractXxx(t).length` (不会被 normalize 掉条), 这是 "pure builder + normalize 兜底" 范式的隐性契约, 任何新加 pure builder 都该用 roundtrip 单测守住, 避免未来下游模块 (e.g. buildStructuredSummary) 把 extract 输出 normalize 一遍突然丢条. **数值范围 sanity 守** — 类似 holding_pct 必须显式 `(0, 100]` 守边界, 防年份末位 / 模板错乱 / 动词后误匹配的 0% / 150% 渗到 downstream (US-029 priority 计算会用 holding_pct 作权重). 接入点 5 步: a) 在原 *.ts service 加 keyword 字典 (Object.freeze 全嵌套) + Max upper bound 常量; b) 加 pure function 主入口 + 接入 builder (与 buildHeuristicNLPResult 同款 sync 路径自然填); c) 字典/常量全 export 便于单测; d) 单测 ≥8 测组 (冻结/优先级 / basic / 阈值边界 / 多锚点 / placeholder name / edgeCases / wiring / roundtrip); e) 验证启发式 fallback 路径 (FAILED payload 不调 normalize, 用占位默认避免远端 AI 借 FAILED 路径渗漏 — 与 US-025 schema 先行同款防御).

- **Learnings for future iterations:**
  - **"接管" vs "追加" 是横切关注点的两种入口形态, 不要混用**: US-022 hard 短路是"主入口 fall-through 替代旧路径" (caller `if(hardResult) return; 旧路径...`), 必须 fail-OPEN 否则旧路径走丢; 本 story 是"主入口跑完后追加旁路" (caller `await quantRun(); await followup()`), 也必须 fail-OPEN 但语义是"主路径已完成, followup 不应让 result undefined". 两者的 META-GUARD 反向断言也对偶 — 接管反向断"旧路径仍存在" (US-022); 追加反向断"helper 不裸调下游" (US-023). 加新 source/新行为类 story 第一步先决策入口形态: fail-CLOSED 挡 (US-011) / short-circuit fail-OPEN 接管 (US-022) / followup fail-OPEN 追加 (US-023) — 这三种形成完整光谱.

- **Learnings for future iterations:**
  - **市场级事件 vs 个人 alert 路由抉择**: 第一直觉看 "依赖: OPS-005" 会想直接调 RiskAlertService.write, 但读 RiskAlertService 实现会发现它强绑 user_id (每条 alert 隶属某用户). critical 公告是市场级事件 (e.g. 茅台被立案), 应该 ops 群所有人都看到, 不属于任何单个用户. 强写 user_id=系统占位 (e.g. 'SYSTEM') 会让该 user 的 AlertsBell 出现一堆不相关公告; 而且每条还要再写 RiskAlert 行 (1000 条公告/天 × 1% critical = 10 条/天 重复 DB 写入). 拆独立 service 走单一 feishu webhook 通道职责清晰. 同款判断适用任何"市场级 vs 账户级"告警 (黑天鹅/政策/行业事件 vs 个人持仓告警/止损/Re-balance), 拆分边界是 "是否属于具体 user".
  - **lazy-require 防循环依赖 + AnnouncementNLPRecord 共享类型**: CriticalAnnouncementPushService import AnnouncementNLPRecord/AnnouncementPriority 类型 (top-level 静态 import OK, 因为只是 type), 但 AnnouncementNLPService 调 criticalAnnouncementPushService 必须 lazy require (runtime require, 防 ES module 循环依赖死锁). 这是单向数据流契约: 上游 publisher (NLP) 通过 require 拉下游 consumer (Push), 下游静态 import 上游 type. 任何 "下游 service 反向被主管道调用" 都按这模板.
  - **截断保留尾行的非对称模式**: 一般截断是 `slice(0, MAX) + '...'`, 但对告警文本必须保留 "触发规则" 尾行 (ops 收到截断消息也能知道是哪条规则触发的, 否则只看到半截标题不知道为啥告警). 实现: `head = slice(0, MAX - tail.length - 3); return head + '...' + tail`. 适用任何 "末尾有元信息" 的告警/日志截断场景 (rule_id / trace_id / timestamp 等).
  - **截断尾部登记 skip_reason='truncated_batch'**: 默认 cap=20 防风暴, 但极端日 30+ critical 会被静默丢. 解法是把超 cap 的尾部 records 也加进 items[] 但 skip_reason='truncated_batch', 让 ops 在 syncDate 返回里能看到 "今天 critical 数超 cap 被截断" 这一事实 + logger.warn 一次. 静默丢失是 "fail-silent" 反模式, 必须显式登记让上游可见.
  - **顶层 try-catch 用 Object.defineProperty getter throw 触发**: 测 top-level catch 时, 内部 loop 已有 try-catch 吞了 poster throw, 想触发 top-level 需要在 records.filter / shouldPushRecord 阶段就 throw. 标准技巧: `Object.defineProperty(badRecord, 'priority', { get() { throw new Error('boom'); } })`, 让 .filter 内 .priority 读取就炸. 这是 "测顶层兜底" 的通用模板 (复用了 US-018 / US-019 / US-022 同款 fail-safe 测法).
  - **persisted=true 双重 gate 防 dry_run 误推**: shouldPushRecord 不光看 priority='critical' 还要 record.persisted=true. AnnouncementNLPService dry_run 路径会把 records 全标 persisted=false (没真落库), 此时哪怕 priority=critical 也不应推飞书 (UI 预演不应触发真消息). 不是把 dry_run 判断写在 service 里 (那只能由 caller 显式传), 而是写在数据 schema 上 (persisted 字段是数据级真相), 任何 caller 误把 dry-run 数据传过来都自然 skip. 同款思想适用 "数据状态 gate 而非 caller flag gate" — 把 fail-safe 写到数据契约里更可靠.
