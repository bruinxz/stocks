# Ralph Progress Log — QuantX A-Share Alpha Refactor

## Codebase Patterns

### Frontend
- **Frontend workspace shells live under** `frontend/src/pages/workspace/`. Each is lazy-loaded in `frontend/src/App.tsx`. When adding workspace tabs in later stories, edit the shell file in place — do NOT introduce parallel page files.
- **All 6 workspace shells use `WorkspaceLayout`** (`frontend/src/components/layout/WorkspaceLayout.tsx`). When a future story adds real content for a workspace, render the new tab UI as `children` (or branch on `activeKey`) and leave the KPI strip / side rail handled by the layout — do NOT rebuild the chrome from scratch.
- **WorkspaceLayout props contract:** `tabs[]` (each `{key,label,icon?}`) → 220px left rail; `kpiSlot` → centered metrics inside the 96px KPI bar; `headerActions` → right-aligned `Space`; `activeKey` / `onTabChange` are required to drive the side-rail selection.
- **App.tsx single source of truth** for routes and the top-level menu. The `routeSelectionAliases` array maps legacy paths to the workspace whose sidebar entry should be highlighted; the `<Routes>` block defines the actual `<Navigate>` redirects. Whenever a legacy path is deprecated, update BOTH arrays.
- **Legacy page imports** are kept (under `/legacy/*` routes) so deep links and embedded iframes still resolve. Only physically delete a page file after all six workspaces have absorbed its functionality (stories US-015..US-018).
- **Workspace shell CSS lives at the bottom of `frontend/src/index.css`** under a `Workspace shell (US-002)` banner. The shell uses `.workspace-shell`, `.workspace-kpi-bar__inner`, `.workspace-side-tabs`. Media query at 1024px stacks the side rail above content.
- **Per-workspace `<name>Service.ts` (US-015+) under `frontend/src/services/`** is the API client layer. Each service file co-locates types with the function that uses them (e.g. `FactorOverviewResponse` next to `listFactorsOverview()`). The service layer **unwraps the `{success,data}` envelope** and throws a JS Error on `success=false`, so components consume the inner `data` directly without re-extracting. Bundled `<name>Service` default export sits alongside named exports for tree-shaking. `frontend/src/services/factorService.ts` is the reference (calls `/factors/overview`, `/factors/preview`, `/strategies/multi-factor/latest-picks`).
- **Workspace data-fetching cadence (US-015 reference):** (1) **Eagerly Promise.all** the data that paints initial KPI + Tab 1 on mount; (2) **lazy-fire** for tabs whose data is triggered by user action (POST `/preview` only when button pressed); (3) keep a **single top-level `loadError`** that replaces the entire body when set — avoids per-tab empty-state misdirection. Don't refetch on tab-switch alone.
- **Workspace large-tab decomposition (US-016):** when a single tab's body exceeds ~150 lines, split into same-file sub-components (`MyStrategiesTab` / `NewBacktestTab` / `CompareTab`), pass state via props, keep the parent only for layout / routing / shared state. Sub-components stay module-private (no export). Shared helpers (`fmtPct` / `percentTag` / `compactDate` / `statusColor` / `statusLabel`) collect at the file BOTTOM. Polling `useEffect` with `window.setInterval` + `setPollingTaskId(null)` exit-condition is the standard cadence; refresh the list inside the interval so when user switches tabs they don't see stale data.
- **Antd `InputNumber<number>` explicit generic** is required when both `formatter` and `parser` are used — without it, TS infers `value: 10000 | 100000000` from the `min`/`max` literals and rejects the parser's `number` return. Pattern: `<InputNumber<number> min={10000} max={100000000} parser={v => Number(v || '') || 0}>`.
- **Recharts multi-series 必须共享 X 轴**：N 条曲线叠加时 `data` 是 **一个** array `[{date, task_5: 12.3, task_8: 9.8, ...}, ...]`，每个 `<Line dataKey="task_N" />` 取一列。**不能** N 条线各自 N 个 data array — 那是 chart.js 的旧模式，recharts 下会 X 轴对不齐。组装时用 `Map<date, row>` 累积，最后 `.sort()` 输出。
- **Inline 表格编辑 hoist state 到 tab 级** (US-017): 用 `editingPositionId / editingValue` 两个 React 受控 state 控制 cell 分支 render (editing vs display)，不要走 antd Table 的 `record.editable` (那是 form-driven 模式，async save + 错误重试难协调)。Display 模式用 Tag + ✏ 按钮；Edit 模式 InputNumber + ✓ 保存 + ✗ 取消。保存失败保留编辑态 + message.error 让用户重试不需重输。
- **行级 destructive 操作三件套** (US-017): `<Popconfirm okButtonProps={{ danger: true }}>` + `<Button danger loading={closingSymbol === row.symbol}>` + `closingSymbol: string | null` 状态隔离 (只锁该行不锁全表)。成功后触发整体 refresh (单字段 patch 不行：平仓影响 cash + total_value + positions + trades 全部链路)。
- **3 列 Card + per-block error 模板** (US-018): 多 source 对比型工作区 (TodayWorkspace 三策略对比 / 未来 US-019..US-023 加策略) 用 `<Row gutter={[16,16]}><Col xs={24} lg={8}>` 3 列布局，每个 Card 顶部 mini-KPI `<Space size={24}>` 三件套 + 主 Table + `error?: string` 字段时显示 `<Alert type="warning">`。一个数据源缺失不会把整页打挂，用户看到的是"X 缺数据"而不是"功能坏了"。
- **跨工作区跳转用 `useNavigate('/workspace/portfolio')`** (US-018 first usage): react-router v6 模式，从 react-router-dom 直接 import `{ useNavigate }`。一键操作 → 弹 Modal 展示明细 → 2 秒延时 `setTimeout(() => navigate(...), 1800)` 跳转，让用户看到结果。**不要用 `window.location.href`** — 会触发 full-page reload 丢失 SPA state（包括 Redux store + antd ConfigProvider 等）。

### Backend
- **PaperTrading services live under `backend/src/portfolio/internal/`**, not `backend/src/services/` (US-003 refactor). The public surface is `backend/src/portfolio/PaperTradingFacade.ts` exposing **exactly 7 methods**: `getPortfolio`, `placeOrder`, `closePosition`, `getDailySnapshot`, `attributePnl`, `applyAutomation`, `getRiskProfile`. Controllers MUST only import the facade. Other services/scripts/jobs may still import from `internal/` directly (the facade-only constraint is the controller boundary).
- **When adding a new paper-trading action**, extend the discriminator union (e.g. `ApplyAutomationAction`) inside `PaperTradingFacade.ts` — do NOT add an 8th method. The `switch` blocks use a `never`-typed default branch to catch missing cases at compile time.
- **Endpoint sub-resources MUST be registered before `:param` catchall (US-015 lesson)**: Express routes are matched top-down, so `GET /api/strategies/multi-factor/latest-picks` MUST be `router.get('/multi-factor/latest-picks', …)` BEFORE `router.get('/:strategyId', …)`. Otherwise the param catchall consumes "multi-factor" as `strategyId` and returns 404 from the unrelated handler. Any new sub-resource on an existing `:param`-style router needs the same upfront placement — add a comment "Must be registered before /:strategyId" so future contributors don't reorder it for "alphabetical neatness".
- **Constants re-exported by facade:** `DEFAULT_PAPER_TRADING_INITIAL_CAPITAL`, `AUTONOMOUS_PORTFOLIO_NAME`, `DEFAULT_AUTONOMOUS_INITIAL_CAPITAL`, `QUANT_ONLY_PORTFOLIO_NAME`. These were previously exported from `PaperTradingAutomationService` and `PaperTradingDashboardService`; controllers/tests now pull them from `../../portfolio/PaperTradingFacade`.
- **Quant services live under `backend/src/quant/{engine,backtest,performance,health}/internal/`** (US-004 refactor). The public surface is **exactly 5 classes**: `StrategyEngine` + `SignalEngine` (engine/), `BacktestEngine` (backtest/), `PerformanceReporter` (performance/), `QuantHealthMonitor` (health/). Controllers MUST only import these 5 facades; non-controller code (Scheduler, Jobs, sibling Services) may still reach into `internal/`. The facade design and method index live in `backend/src/quant/CLAUDE.md` — update that, not this file, when adding new facade methods.
- **Cross-layer sibling imports inside quant** use explicit `../../<layer>/internal/...` paths (e.g. `engine/internal/QuantFusionService` imports `quantRuntimeHealthService` from `../../health/internal/QuantRuntimeHealthService`). Don't add wildcards or re-export barrels — staying explicit makes the inter-layer graph visible to future readers.
- **`QuantMath.ts` and `StrategyRegistry.ts` stay at `quant/engine/` top level** (NOT in `engine/internal/`). They're imported by every strategy under `strategies/`; moving them would force strategies to reach into `internal/`. Treat them as shared primitives, not part of the facade-internal split.
- **JSONB column mutation requires `model.changed('field', true)`** (US-017): Sequelize 的 dirty-check 对 JSONB 列上的 in-place mutate (push/splice) 或 reassign 都不会自动包含到 `_changed` set 里。任何 JSONB array/object 修改后必须 `model.changed('user_notes', true)` 显式标记，否则 UPDATE SQL 不发。`appendNote` 用 `journal.user_notes = [...existing, note]` (reassign) + `journal.changed('user_notes', true)` 双保险。
- **"懒建档" 模式** (US-017): 用户写操作如果发生在 "主数据由 AI 生成 + 用户补充" 的领域里 (复盘日记追加手记 / RiskAlert 备注 / RecommendationFeedback)，遇到该主数据还不存在时 endpoint 自动 create 一行 placeholder (字段标识清晰: `mood='未生成'` 或 `is_placeholder=true`) 让用户操作能继续而不被 404 拦截。前端用 placeholder 标识区分 "AI 已生成" vs "纯用户操作"。
- **facade 扩 action 联合类型而非加方法** (US-003 规则, US-017 实践): PaperTradingFacade 严格保持 7 个 public method (`getPortfolio / placeOrder / closePosition / getDailySnapshot / attributePnl / applyAutomation / getRiskProfile`)。新写操作就扩展最近 method 的 `XxxAction` / `XxxView` 联合类型 + switch case (default branch `const _: never = action` 保证 exhaustive check)。US-017 加 stop-loss 时套用：`ApplyAutomationAction += 'set_stop_loss'`，applyAutomation switch += 1 个 case，不破坏 facade 收敛。
- **工作区聚合 service per-block error fallback** (US-018): `getXxxSignals()` 用 `Promise.all` 并发跑 N 个独立查询，每个 catch 成自己的 fallback object 带 `error?: string` 字段。**任一查询失败不能阻塞其他**——前端按需在该 Card 顶部显示 `<Alert>`。`TodaySignalsService` 是模板：3 策略 + 账户 + 告警 + 事件 = 6 个并发分支，全部 catch fall back。一键操作 endpoint (`applySignals`) 先重新跑一次 `getSignals` 保证下单决策与 UI 一致，再用 `paperTradingFacade.placeOrder` 逐笔下单（不绕开 facade —— 否则 risk profile / automation hook 错位）。**已持有 + 本批次重复都要 skip**，避免一键下三次。

### A-share data ingestion (US-005+)
- **New data sources live in 3 paired files**: `backend/src/models/<Source>.ts` (Sequelize model, register in `models/index.ts` AND `config/database.ts`), `backend/src/data/sources/<Source>Client.ts` (Python helper wrapper), `backend/src/data/services/<Source>SyncService.ts` (DB write + range/checkpoint). Add a CLI under `backend/src/scripts/sync-<source>.ts` and a `sync:<source>` npm script. The northbound trio is the canonical reference.
- **AKShare Python commands live in `backend/python/akshare_helper.py`**. Add a new function + a dispatcher case in `main()`. Always (1) accept both `YYYY-MM-DD` and `YYYYMMDD` and convert internally, (2) build a柔性 col_map (Chinese column headers drift between akshare versions), (3) include the full original row as `raw_payload` for audit, (4) return `[]` (not raise) on empty data so the TS layer can checkpoint a "tried but empty" day separately from a hard failure.
- **Idempotent reruns = composite-PK + `bulkCreate` + `updateOnDuplicate`**. Always include `updated_at` in `updateOnDuplicate` so ops can see refresh times. Default `syncRange` to skip-existing for cheap catch-up; expose `--force` for backfills.
- **Multi-record-per-stock (US-006 龙虎榜) ⇒ N-tuple PK**: when one stock spawns many rows per day (e.g. `buyer_seat × seller_seat`), the model PK is a 3-/4-tuple. Do the cartesian fan-out IN the Python helper so the TS service stays a clean `bulkCreate`. Keep both halves in `raw_payload` (`{list_row, buyer_row, seller_row}`) for audit.
- **Business-logic tagging (e.g. `is_famous_yz`) belongs in the TS service**, NOT the Python helper. Python is the dumb fetcher; TS owns whitelists like `backend/src/constants/famousSeats.ts` so the rule can evolve without re-running Python.
- **Cross-day derived fields (e.g. `continuous_days` 连板天数) belong in the TS service** — `LimitUpSyncService.syncDate` looks back 5 calendar days of LimitUpStock history before each `bulkCreate` and recomputes `CD = yesterday.CD + 1` (max with akshare's own value as a floor). Pattern for any field that depends on previous-day records: `loadRecentHistory()` → map override → bulkCreate.
- **Multi-endpoint merge (US-007 涨停 zt_pool + strong_pool)**: when AKShare has two endpoints with overlapping rows + each-side-unique extras, pick one as primary (zt_pool), index the other by stock_code as a side-car dict in Python, then 1-pass merge in `_, row in df_primary.iterrows()` + emit secondary-only rows in a final loop using a `seen_codes: set` guard. Keep both raw rows in `raw_payload = {primary_row, secondary_row}`.
- **AKShare time-of-day strings are inconsistent** (`"09:25:03"` or `"92503"`). Parse digits-only in the Python helper (`_is_one_word(limit_up_time, open_times)` in `akshare_helper.py`) — let TS consumers see a pre-computed boolean instead of re-parsing. Counterpart for `is_famous_yz`/whitelists is in TS — divider: per-row computation that's pure data goes Python-side; rules that may evolve or need DB joins stay TS-side.
- **Helper micro-functions to copy across AKShare commands**: `_cell_str / _cell_float / _cell_int / _row_to_jsonable / _format_iso_date` in `akshare_helper.py` — defined once for US-007, reuse them in future commands (`get_industry_flow`, `get_earnings_forecast`, etc.) instead of repeating `safe_float_value(row.get(col)) if col else None`.
- **Multi-endpoint join WITHOUT a shared key (US-008 行业资金流)**: `stock_sector_fund_flow_rank` has metrics but no board code; `stock_board_industry_name_em` has the code but joins by Chinese 板块名称. Indexing the smaller "name→code+metadata" df into a Python dict, joining per row, and emitting `industry_code = "FALLBACK-<name>"` for unmapped names keeps rankings intact. **Cross-DB joins (e.g. `limit_up_count` requires JOIN-ing LimitUpStock by industry name) belong in the TS service, not Python** — same divider as `is_famous_yz` and `continuous_days`.
- **Real-time-only snapshots (US-008 fund_flow / name / cons family)**: a subset of AKShare endpoints CANNOT replay history; you only get "now". The `date` param becomes a `trade_date` LABEL stamped onto each output row by Python — the data is still today's. Document this on the client jsdoc + service jsdoc; don't pretend `--start=2023-01-01` does what it appears to. Schedule once per day post-close; the `INDUSTRY_FLOW_TIMEOUT_MS` default is 240s because per-board `cons_em` fetches dominate (~86 boards × AKShare rate-limit).

### Quant factor infrastructure (US-009+)
- **Factor module tree** lives at `backend/src/quant/factors/` and is the **only** place where factor logic exists: `types.ts` (Factor interface + FactorContext), `FactorRegistry.ts` (singleton — same dedupe-on-register pattern as StrategyRegistry), `FactorPipeline.ts` (cross-sectional batch processor), `normalization.ts` (winsorize/zscore/percentileRanks — **cross-sectional** helpers, NOT to be confused with quant/engine/QuantMath.ts which is time-series). `library/index.ts` is the import-time aggregator: each factor file self-registers via `factorRegistry.register(...)` and gets pulled in by `library/index.ts` so callers only need `import '../quant/factors/library'` once.
- **Factor design contract**: factors output **un-normalized** raw_value Map<stock_code, number|null>. The Pipeline does winsorize(1%-99%) → zscore → percentileRanks across the cross-section. Factors that self-normalize would break cross-factor comparability — **never** call zscore() inside a Factor.compute().
- **Sparse Map is fine**: if a factor can't compute a value for a stock (missing data), just don't include it in the Map. The Pipeline fills the universe gap with a "neutral row" (raw_value=null, z_score=0, percentile=0.5) so factor_scores always has `universe_size` rows per (date, factor) — makes multi-factor JOIN-free.
- **stock_code is suffix-less**: FactorScore.stock_code matches NorthboundHolding/LimitUpStock/IndustryFlow ("600519", not "600519.SH"). When a Factor.compute() reads Stock/DailyBar (which use "600519.SH"), it MUST `symbol.split('.')[0]` before keying the output Map.
- **Pipeline serial-by-factor, not Promise.all parallel**: one bad factor doesn't kill the batch; logs stay readable; debug is straightforward. The compute step within one factor can still batch DB queries internally.
- **library/_helpers.ts** (US-010) is the **library-internal** shared utility module — prefix `_` = "only library code should import this; not exposed via quant/factors/index.ts". Provides `stripSuffix(symbol)`, `inferStockSymbol(code)` (reverse: "600519" → "600519.SH"), `loadStocksByCodes(codes, attrs)` (one-shot batch query that returns Map<stock_code, Stock>), `isFiniteNumber(v)`, `lookbackStartDate(asOf, days)`. Use these in every new factor — don't inline the 5-line symbol-mapping logic 8 times.
- **3 query-shape patterns** to copy when adding a new factor (US-010 codified them):
  - **"Time-series aggregate" (quality/growth)**: pull `factor_date ∈ [as_of - N天, as_of]` from a `symbol`-keyed source table, group by symbol in-memory, then stripSuffix → output.
  - **"Time-series + cross-section" (momentum/low_vol)**: `loadStocksByCodes(universe)` first to get `Stock.id`, then `Op.in: stock_ids` + time range on DailyBar; group by stock_id, `arr.sort((a,b)=>a.time-b.time)`, count back from tail to align on T-N.
  - **"Suffixless-table direct" (northbound/dragon_tiger)**: `Op.in: ctx.universe` + trade_date window — stock_code field IS the output key, no Stock lookup needed.
- **Z-score-friendly raw_value shapes** (US-010 lessons):
  - For "event count" factors (dragon_tiger), use **distinct DAYS** not raw rows — cartesian fan-out in source tables inflates counts unpredictably.
  - Don't write `0` when "未触发" — leave the stock out of the Map so Pipeline's middle-rank neutral default (percentile=0.5) applies; writing 0 collapses the cross-section to a "0 vs positive" bimodal distribution that breaks z-score interpretability.
  - For "lower-is-better" factors (low_vol), return `-stddev` not `1/stddev`: avoid div-by-near-zero noise.
  - For "ratio family" factors (value), use `1/PE + 1/PB` not `-PE - PB`: keeps both ingredients dimensionless and naturally bounded.

### Quant strategies — 组合级 vs per-stock (US-011+)
- **Two strategy shapes coexist in `backend/src/quant/strategies/`**: the historical **per-stock `evaluate(context)`** pattern (17 strategies, called by StrategyEngine in a stock×strategy matrix), and the **组合级 async `generateSignals(date)`** pattern (introduced by US-011 MultiFactorAlphaStrategy). Picking the wrong shape forces you to encode 横截面 / top-N / 行业中性 / previous-diff logic into a per-stock evaluate — don't do it.
- **组合级 strategies still extend `QuantStrategy`** for registry contract, but `evaluate()` returns an informational `signal='hold'` with `factors.note='use_generateSignals_instead'`. Real entry point is the async `generateSignals(date, { params?, previousSelection? })`.
- **DataSource interface injection is mandatory for 组合级 tests** — every 组合级 strategy declares a `<Name>DataSource` interface + `Default<Name>DataSource` Sequelize impl + `PRODUCTION_DATA_SOURCE` singleton, and constructor accepts an override. Tests inject a fake `loadXxx()` returning Map<…>, completely bypassing DB. See `MultiFactorAlphaStrategy.ts` for the canonical layout.
- **BUY/SELL/HOLD diff lives in the strategy, not the caller.** Caller passes `previousSelection: string[]`; strategy computes `BUY = target ∩ ¬prev`, `HOLD = target ∩ prev`, `SELL = prev ∩ ¬target`. Letting N callers each diff = N inconsistent diff implementations (the bug PaperTradingFacade already paid for).
- **Stable tie-break in candidate sort = `stock_code.localeCompare`** — otherwise V8 TimSort plus comparator returning 0 makes monthly-rebalance boundary picks non-deterministic, breaking audit / replay / reconciliation.
- **`override.weights` replaces default wholesale, NOT spread-merge** — users expect "what I list is the whole spec". Spread merge silently keeps 6 default factors in the weighted sum and breaks composite math. Same lesson applies to any new Record/object param in 组合级 strategies; scalar params (topN, maxPerIndustry) are safe to default.
- **Tests live in `backend/tests/strategies/`** (per AC). The dir is **outside** `tsconfig.json`'s `include` (which is `src/**/*`), so `npx tsc --noEmit` and `npm run lint` skip it. Tests use the node-direct convention (no jest) — `npx ts-node --transpile-only tests/strategies/<Name>.test.ts`. Pattern matches existing `productionPreflight.test.ts` / `LiveAuditAlertService.test.ts` / `liveTradingRateLimit.test.ts` in `src/`.
- **`backend/src/quant/strategies/CLAUDE.md` is the source of truth** for the 组合级 pattern + 5 design constraints (DataSource injection, BUY/SELL/HOLD in strategy, evaluate-as-hold, stable sort tie-break, tests-in-backend/tests/). Update it (not this file) when refining the contract.
- **组合级 strategies pick `previousSelection` schema based on exit needs (US-012)**: `string[]` is sufficient when调仓 only needs set membership (MultiFactorAlpha 月度调仓); `Position[]` with structured fields (entry_date/entry_price/half_exited) is required when exit rules depend on per-position state (DragonHead 止损 / holding_days / 防重复减半). New signal types beyond BUY/SELL/HOLD (e.g. `sell_half`, `add`, `scale_out`) are similarly tied to the strategy's domain — extend the signal union and document each state's trigger + caller撮合 action in the .ts jsdoc; recap in `strategies/CLAUDE.md`. `MultiFactorAlpha` and `DragonHead` are the two canonical references for "lightweight" vs "stateful" position schemas.
- **Event-driven strategies (US-013) — sparse-day return is NORMAL**: 业绩预告一年只有 4 个集中披露期，平日 generateSignals 返回 `eligible_count=0` 是预期行为，不要把"无信号日"当成数据缺失告警，否则告警噪音淹没真正问题。事件触发 + 多源双确认的策略统一在 DataSource 接口里给每个数据源独立 `loadXxx()`，单测可独立 mock。判定顺序遵循"早过滤先做"：事件源 → 元数据 → 多源历史回看，避免反向次序浪费 IO。
- **Report-period-keyed data sources (US-013 业绩预告)**: AKShare `stock_yjyg_em` / `stock_yjbb_em` / `stock_yjkb_em` 按 **报告期** 检索（不是公告日）。Sync 服务对应 `syncReportPeriod(period)`，模型 PK 包含 `report_period` 字段（3-tuple）；CLI 暴露 `--year=YYYY` 一键展开 4 个季度末。**业务超预期判定（is_surprise）留 TS 服务**，符合"Python 是 dumb fetcher / 业务规则可演化留 TS"的统一切分。
- **跟随类组合级策略 vs 事件驱动 (US-019)**: 跟随类（北向 / 主力资金 / 融资余额）的触发源是"每日全市场都有的连续信号"，所以 DataSource 接口的 `loadCandidateXxx(asOfDate, params)` **不接受 stockCodes 列表**——它自己输出 universe。同源数据（如 ratio 快照）必须在主流程 `generateSignals()` 里拉一次然后传递给 `evaluateEntries` / `evaluateExits`，**不要**在两个 evaluate 内部各自重复 fetch。跟随类策略**必须**有 "反向信号出场线"（北向减仓 → SELL）；少了它就退化为"被动止损 + 持有期到期"，丢失 alpha 来源。出场优先级 A→B→C = 硬约束（到期 / 止损）> 软信号（北向减仓），避免短期噪音过早赶走浮盈持仓。完整 4 strategy 对比表在 `backend/src/quant/strategies/CLAUDE.md`。

### Backtest engine — A 股执行约束 (US-014+)
- **`AShareConstraintEngine` 是无状态纯模块** at `backend/src/quant/backtest/AShareConstraintEngine.ts`。三个方法：`evaluateOrder(ctx)` 返回 `{ok, reason?, detail?}` 决定能否成交（T+1 / 涨跌停 / 停牌 / ST 过滤 / 流动性门槛）；`computeFees(amount, side)` 返回 commission + stamp_tax + transfer_fee 三段费用 breakdown；`executionPrice(bar, side, timing)` 给三种 timing (next_open / same_close / twap_proxy) 的成交价并附动态滑点。引擎严格无 DB 访问、无状态字段、不修改输入参数——多策略并发跑零状态污染。
- **`RejectionReason` enum 是统一拒单原因码**。下游 `block_reasons` counter 与 `RejectedOrder.reason` 字段都从同一 enum 取值，UI/聚合统计/告警有单一事实源。新增拒单原因必须先扩 enum 再用（free-text reason 会破坏 aggregation）。**`isSTName` 在 `AShareConstraintEngine.ts` 与 `MultiFactorAlphaStrategy.ts` 各有一份**——任何改判定逻辑必须同步两边。
- **`rejected_orders` 是 audit trail，`block_reasons` 是 aggregate twin**：每条 rejected_order 含 `{trade_date, strategy_key, symbol, side, reason, detail?, reference_price?}` 写入 `QuantBacktestResult.rejected_orders_json` (US-014 新增列, defaultValue=[] 旧记录 NULL-safe)；同时 `diagnostics.block_reasons` 维护 `Record<reason, count>` 的聚合视图。UI 中"为什么这只票没买/卖成"用 audit；dashboards/heatmaps 用 aggregate。两者并行因消费方不同。
- **费率默认匹配主流互联网券商 2024-2026**：commission 万 2.5 双边 + min 5 元，stamp tax 千 1 卖出单边，**transfer fee 万 0.1 双边**——过户费是第三方回测最常漏算的项，US-014 强制总是收取。`computeFees()` 一次返回 `FeeBreakdown` 让 caller 清晰看到每段费用，不要再分散在 inline 计算里。
- **3 种 execution_timing**: `next_open`（次日开盘 + 0.2% 滑点，默认）/ `same_close`（当日收盘 + 滑点）/ `twap_proxy`（(open+high+low+close)/4 + 滑点，简单 VWAP 代理，适合龙头/短线策略）。`twap_proxy` 比 `next_open` 更难"完美捕捉"开盘脉冲，回测结果更保守贴近真实；不强制策略层选 timing，让回测者按策略性质选。动态滑点按 turnover 分段（≤ 0 → ×2，< 30M → ×1.8，< 100M → ×1.25，其他 ×1.0）。
- **回测引擎仅做撮合调度**：`QuantBacktestEngine` US-014 后只负责日期 loop / 仓位 bookkeeping / 候选排序；约束 + 费率全部 delegate 给 AShareConstraintEngine。每个策略 instantiate 一个 constraintEngine（构造时 copy settings，互不干扰，未来可支持"按策略 override 部分约束"）。
- **回测测试在 `backend/tests/backtest/`** (新目录, 与 strategies/ 同款约定)，跑法 `npx ts-node --transpile-only tests/backtest/<test>.ts`。Mock 策略直接 extend QuantStrategy + 注册到 strategyRegistry singleton (`ensureRegistered(key, factory)` helper 防 dup register)，避免依赖真实策略产出特定信号——好处：测试可以精准 stub "BUY on day 1, SELL on day 3" 这种行为，对约束引擎做 end-to-end 集成。

- **AKShare 列名容易随版本漂移**, especially Chinese column headers (持股数 vs 持股数量, 持股市值 vs 持股市值占A股市值比). Build a柔性 col_map in the Python helper instead of indexing by exact name — otherwise an akshare upgrade silently zeroes out your data.

### Learnings for future iterations
- **龙虎榜 is a 2-API combo, not 1.** `stock_lhb_detail_em` only gives the day's stock list + reason — you MUST fan out to `stock_lhb_stock_detail_em(symbol, date, flag='买入'/'卖出')` twice per stock to get the seat list. The Python helper does this entirely server-side so the TS layer stays declarative.
- **AKShare positional-vs-keyword signature drift is real.** Wrap `ak.stock_lhb_detail_em(start_date=..., end_date=...)` in `try/except TypeError` + positional fallback. Same for `stock_lhb_stock_detail_em`. This saved a 30-minute debug when an older version was installed locally.
- **Composite PK = (date, stock, buyer, seller).** A single LHB stock has ~10 buyers × ~10 sellers = 100 rows; the cartesian shape matters because (a) buyer席位净额 / 卖方席位净额 isn't decomposable per-pair, and (b) it lets short-term strategies join freely without secondary tables. Storing `raw_payload.{list_row, buyer_row, seller_row}` keeps the source of truth recoverable.
- **knowing 游资 ≠ free text matching.** 营业部 names are LONG (`"东方财富证券股份有限公司拉萨团结路第二营业部"` = 23 字符) and AKShare occasionally returns 简写. Maintain (a) a 标准全称 whitelist, (b) an alias map for known 简写, (c) a fuzzy 拉萨系兜底 (`东方财富证券` + `拉萨` always counts) — the three-layer match catches > 95% in practice.
- **`canonicalSeatName` is critical for group-by sanity.** Without it, "中国银河证券绍兴营业部" and "中国银河证券股份有限公司绍兴营业部" would be two different keys in any aggregate over `buyer_seat`. Always normalise BEFORE writing — back-filling normalisations after the fact is painful.
- **The `is_famous_yz` boolean is intentionally minimalist** — boolean instead of `famous_yz_name` (e.g. "赵老哥"). One seat may host multiple traders over time; binding a name into the row would force re-tagging on every regime change. Strategies that need the named alias should JOIN against `constants/famousSeats.ts` at query time.
- **180s timeout was chosen empirically.** ~50 LHB stocks/day × 2 API calls + AKShare's 30s+ rate-limit can push a single-day fetch past 60s. Don't drop below 120s without testing on a real busy day (e.g. 政策性新闻日 = 100+ LHB stocks).
- **`raw_payload.{list_row, buyer_row, seller_row}` recovers everything** if AKShare adds a new column we forgot to map (`持股集中度变化` etc.). When extending the model with a derived field, read from `raw_payload` rather than re-fetching.

### Learnings for future iterations
- **AKShare 不是所有端点都能放回历史**。`stock_sector_fund_flow_rank` / `stock_board_industry_name_em` / `stock_board_industry_cons_em` 都是"当下时刻"的实时快照，没有 date 参数（甚至没有任何时间参数）。CLI 的 `--date` 只是 `trade_date` 标签——历史日期回填会让今日数据被打成历史日期的标签，污染数据库。这是数据源限制，不在服务层隐藏；jsdoc + CLI + service comment 三处都明确写。
- **3 个端点的隐式 join key 是 Chinese 字符串**。`stock_sector_fund_flow_rank` 给 "名称"（无代码），`stock_board_industry_name_em` 给 "板块名称 ↔ 板块代码 BKxxxx" 映射。两者都来自东财，名字基本一致；少量边角情况通过 `industry_code = "FALLBACK-<name>"` 兜底，绝不丢行。
- **86 个行业 × 1 次 cons fetch = 86 次外部请求**，AKShare 限速下单日同步耗时 120-180s。timeout 一定要 ≥ 240s，60s 必超。
- **一字板启发式 = 涨跌幅 ≥ 9.95% 且 振幅 ≤ 0.5%**。振幅缺失时只要涨幅触顶就保守视为一字板（跳过选龙头）。全行业全是一字板时（极端情绪日，比如政策性新闻），退而求其次取涨幅最大行——不能让 `leader_stock_code` 永远是 null。
- **`limit_up_count` 是跨 DB join 字段**：industry_flows 表的填充依赖 limit_up_stocks 表的当日数据，所以 sync 顺序应当是先 `sync:limit-up` 后 `sync:industry-flow`（cron 配置时注意）。若两者并发跑，第一次结果会 limit_up_count=0；下一次 sync 同日时 `updateOnDuplicate` 会修正。这层 ordering 关系在 README 的 cron 一节应该 follow up 加。
- **`industries_with_limit_ups / industries_with_leader` 是 ops 指标**，不仅服务 caller 也服务监控：正常交易日应当 with_leader ≈ 86（绝大多数行业能找到非一字板龙头），with_limit_ups 在牛市能到 60-80、震荡市 5-20、跌市 0-5。某天突然 with_leader=0 就意味着 AKShare 抓数大概率出问题，应触发告警。
- **3 个新的 Codebase Patterns 提炼**：(1) 多端点无共享键 join 用 Chinese name 隐式连接 + FALLBACK 行兜底，(2) 跨 DB join 永远留 TS 服务，(3) 实时快照端点要写明 "date 是标签而非过滤器"。这些会被 US-022 高分红低 PE / US-090 股东增减持 等后续股票/财务接口直接复用。

### Learnings for future iterations
- **3 元组主键 (trade_date, stock_code, factor_name) 是设计核心**。曾考虑用 auto-increment id +
  唯一索引——但 bulkCreate + updateOnDuplicate 对 composite PK 直接支持，省一个 unique constraint
  + 让 "重跑覆盖" 行为最直观。
- **"中性行" 补全是无声的契约**：调用方查 factor_scores 时不需要 LEFT JOIN 处理缺失股票，
  因为每天每因子都保证写满整 universe。raw_value=null + z_score=0 + percentile=0.5 让多因子
  合成 `SUM(z_score * weight)` 自然给缺值股票打 "中性总分"，不会因为单因子缺值就把整只股票剔出。
  US-011 多因子策略可以直接 `WHERE trade_date=? GROUP BY stock_code` 不用关心覆盖率。
- **横截面 vs 时序 normalization 必须分目录**。`quant/engine/QuantMath.ts` 的 mean/stddev 是
  "对一只股票时间序列上的滚动均值/方差"；这里的 mean/stddev 是 "对一组股票同一时点截面值的均值/方差"。
  混用会语义错。命名空间各自独立比 "复用代码" 重要。
- **`Factor.compute` 不写库** 是关键的隔离设计：可以单独跑一个因子拿到 Map 做 debug / 单元
  测试，不需要 DB up；Pipeline 是唯一持久化点，逻辑集中。"compute → persist 分离" 让
  IC 报告 (US-041)、因子热力图 (US-074) 等下游能复用 compute() 输出而不重新写库。
- **Stock.symbol vs FactorScore.stock_code 的格式差异是 US-010 第一坑**：
  老的 Stock / DailyBar / StockValuationFactor 用 "600519.SH" 形式；新的 NorthboundHolding /
  LimitUpStock / IndustryFlow / FactorScore 用 "600519"。在 CLAUDE.md 里写了 `stripSuffix`
  模板代码 + 单元素工具函数，避免 US-010 8 个因子各写 8 次相同的 split。
- **FactorRegistry 全局单例 + 单元测试用 new FactorRegistry() 实例隔离** 是关键模式。
  生产代码（CLI / Pipeline / Strategy）共享单例确保所有因子在一个地方；测试创建独立 registry
  注入到 `new FactorPipeline(registry)` 完全隔离，避免测试间状态污染。`_clearForTesting`
  是 fallback 但鼓励 new instance 模式。
- **CLI 的 `--skip` 与 `--factors` 并存**：白名单 + 黑名单同时支持。--factors 选定一组要跑
  的因子，--skip 在那一组里再过滤。生产场景：cron 跑全部因子 + 黑名单临时下线某个失效因子，
  比改全量列表更安全（一目了然，错过下线就是一次性的）。
- **FactorPipeline 串行调度 vs 并行**：选了串行。8 因子 × 全 A 股 (~5000 只) × ~250 日 lookback
  在 Postgres 上单因子 ~2-3s；串行 8 个 ~20-30s，完全可接受。并行的隐性风险大：
  (1) bulkCreate 同时打满连接池；(2) 日志交错难调试；(3) 单因子 OOM 影响别的。
  改并行的触发条件应当是 "因子数 > 20 且单因子 < 1s" 时再说。
- **`is_active != false` 用 Op.or [{is_active: true}, {is_active: null}]** 是为了兼容
  旧数据（Stock 表里可能有 NULL 的 is_active 字段）。`{is_active: { [Op.ne]: false }}` 看起来更直接
  但 Sequelize 对 `Op.ne` + NULL 的 SQL 行为依赖 NOT NULL 假设，安全起见用 Or 显式。

  `(buyer_seat × seller_seat)` 笛卡尔展开，一只股票一天可能有 5-10 个 famous_yz=true
  的行。`count(笔数)` 让一天爆量游资 vs 持续多天小量游资的票完全不可比；改用
  `count(distinct trade_date)` 让 raw_value 自然在 0..20 之间，横截面 zscore
  收敛漂亮。
- **dragon_tiger 因子的 "缺失 ≠ 0" 决策**：窗口内一个 famous_yz 都没有的股票
  不入 Map，让 Pipeline 中性补全（percentile=0.5）。强行写 0 会让大多数股票
  挤在 raw=0，把横截面均值拖向 0、zscore 分布退化成 "0 vs 正" 二元。"未上榜"
  与 "上榜但被卖" 是不同的事件，前者保持中性才正确。
- **low_vol 用 `-stddev` 而非 `1/stddev`**：避免分母趋零（停牌全程没动）导致数值爆炸；
  取负号让 Pipeline 横截面 zscore 后高分自然代表低波动股，不需要在 strategy
  层颠倒符号。同样的 "符号选择" 思路也适用于 US-029 之后的高阶因子（如换手率
  双向异常打分）。
- **value 用 `1/PE + 1/PB` 而非 `-PE - PB`**：分母倒数自然无量纲，两个比率都
  在 0..1 区间（除非极便宜的烟蒂股），等权相加不会让 PE=100 完全淹没 PB=2；
  反过来 `-PE - PB` 会让 PE 单一信号主导。
- **momentum 用 `close[T-20]/close[T-120] - 1` 而非 log return**：A 股极端值
  比海外多，对数收益会让极端涨幅更"重"；用比值差 + Pipeline 1%-99% winsorize
  组合反而稳定。120-20 这个 "skip recent 20 days" 设计是经典学术因子（Jegadeesh &
  Titman 1993 + 后续 follow-up）——A 股短期反转特别强，剔除最近 20 日效果显著。
- **`loadStocksByCodes` 的设计权衡**：4 个因子（momentum/low_vol/value 间接/money_flow）
  都需要 universe→Stock 反查；如果每个因子各自 `Stock.findAll({where:{symbol:{[Op.in]:...}}})`
  就是 4 份几乎相同的代码。抽到 `_helpers.ts` 后单点优化（attributes 投影、是否需要 `raw:true`
  等）一次性生效。但**没有把所有数据访问都抽成 DAO**：因子查询 shape 异质性大
  （momentum 要 time-series stock_id JOIN、quality 要 symbol GROUP BY），强行抽
  会让接口爆炸。只抽 "8 个因子里 ≥3 个都用" 的部分。
- **横截面 z-score 友好的 raw_value 形态是 US-010 最大的设计教训**：写完所有 8 个
  因子后回头看，每个都有一个 "怎么把现实信号编码成横截面良性分布" 的小决策。
  CLAUDE.md 把这 4 条（"独立日数 vs 笔数"、"缺失 vs 0"、"-x vs 1/x"、"1/a + 1/b vs -a - b"）
  落在 "横截面 z-score 友好的 raw_value 形态" 一节，US-029+ 加新因子时直接对照。
- **MomentumFactor / LowVolFactor 用尾部计数而非日历对齐**：用 `arr.length - 1 - 20`
  而不是按 `as_of - 20 个日历日` 查询。原因：A 股节假日（春节 7 天、五一 5 天等）
  让 "20 个日历日前" 与 "20 个交易日前" 经常差 5-10 天；尾部计数永远是 "我有的最近 N 个交易日"
  而不是 "日历上 N 天前应该有的"。`QUERY_CALENDAR_DAYS = 220` 足以覆盖 120 个交易日
  + 春节假期 + 一些缺数据缓冲。
- **新因子文件**：要复用 `_helpers.ts` 的 5 个 primitive，**不要**inline 5 行
  `if (!symbol) return ''; const i = symbol.indexOf('.'); return i < 0 ? symbol : symbol.slice(0, i);`
  ——库内已经有 `stripSuffix(symbol)`，统一了 8 份不一致的边界处理。
- **Worktree gotcha (still active)**：before `git add`, `rm backend/node_modules`（symlink 污染 git status）。

### Learnings for future iterations
- **组合级策略 vs per-stock evaluate 是 codebase 的 first-class 区分**。
  US-011 后 `strategies/` 同时存在两种形态；新加策略前先决定形态再写代码：
  trend / momentum / 突破/ 反转/ 防守 类几乎都是 per-stock evaluate；
  多因子合成 / top-N / 行业轮动 / 北向跟随 / ensemble 几乎都是组合级。
  混用同一接口意味着把不适合的逻辑硬塞进 evaluate() — 不要这么做。
- **DataSource 接口注入是组合级策略的"测试解锁键"**。曾经犹豫"直接在
  策略里 `FactorScore.findAll` 不行吗？"——行，但**测试就必须跑真 DB**，
  CI 慢、隔离差、fake 数据难造。加一层接口（MultiFactorAlphaDataSource +
  生产实现 + PRODUCTION_DATA_SOURCE 单例）让 17 个用例都跑 in-memory fake
  数据，整套测试 < 1s 完成。代价：每个策略要写 ~30 行 DataSource 接口 +
  生产实现，但 ROI 极高——后续 US-019/020/021 应当原样复用模式。
- **override.weights 必须整体替换 default 而非 spread 合并**。原以为
  `{ ...def.weights, ...override.weights }` 用户友好，写完测试才发现：
  用户只想给 value=2, momentum=8 → 实际跑的是 8 因子加权 (其他 6 因子
  还在 0.10-0.15)，composite 算出来根本对不上预期。改成"如果 override
  里有 weights，整体替换"才符合直觉 (用户的心智模型: 列出的就是全部)。
  类似陷阱在 `topN` / `maxPerIndustry` 等标量参数上不存在，**只有
  Record/对象参数会踩**，下一个组合级策略加入新对象参数时记得复查。
- **排序稳定性 tie-break = stock_code 升序** 是月度调仓的隐性硬性要求。
  V8 的 Array.sort 是 TimSort (stable in ES2019+) 但 comparator 返回 0
  仍然依赖原数组顺序——这意味着 universe 内 stock_code 的入栈顺序会
  影响 boundary 的结果。显式 `localeCompare` tie-break 让"同一 (date,
  factor_scores 快照, 参数) 跑出的结果完全相同"成为强契约——审计 /
  对账 / 回放都依赖这一点。
- **`factors.note='use_generateSignals_instead'` 是机器可读的提示**。
  evaluate() 返回的 reasons[] 是给人看的；factors 对象里塞一个
  enum-like 字段让 downstream 工具 (例如 backtest engine 自检) 能
  识别 "这只信号被策略主动声明不可信"。后续组合级策略一律按这个 key
  写，便于全局 grep。
- **测试架构的妥协**：AC 要求 `backend/tests/strategies/` 路径，但
  codebase 既有测试都在 `src/**/*.test.ts` 紧邻源码。最终选择尊重 AC：
  tests/ 目录在 tsconfig 的 `include` 之外 → 不被 typecheck 带入 →
  ts-node `--transpile-only` 跑零依赖，干净。eslint 默认只扫 `src/`，
  tests/ 也不会被 `npm run lint` 触发，不污染日常 lint 噪音。
  下一个组合级策略测试就放 `backend/tests/strategies/` 即可。
- **Worktree gotcha (still active)**：before `git add`, `rm backend/node_modules`
  (symlink 污染 git status)。

## 2026/06/07 - US-012

### What was implemented
短线龙头战法策略：`DragonHeadMomentumStrategy`，第 2 个组合级策略。

抓取强势行业内首板/低连板（1-3 板）梯队龙头：当日涨停 + 知名游资席位
净买入 + 流通市值 30-200 亿 + 所属行业当日资金流排名前 10。次日开盘
高开 5%+ 减半、炸板 / 持有 3 自然日强制平仓。

**与 MultiFactorAlphaStrategy 的关键差异**：

1. **事件驱动**而非月度调仓 — 每个交易日触发 generateSignals(date)。
2. **`currentPositions` 比 `string[]` 复杂** — 每只持仓需带 entry_date /
   entry_price / half_exited，因为 exit 规则要算 holding_days、止损 pnl、
   防重复减半。这是 schema diff 从 MultiFactorAlpha 的合理扩展。
3. **新信号类型 `sell_half`** — 高开减半时保留剩余仓位且标 half_exited=true。
4. **target_positions 是 Position[]** 而非 string[]，对应上面 schema 扩展。

**入场 5 维 AND 过滤**（按性能从快到慢编排，早 filter 早跳出）：
1. 当日涨停（LimitUpStock 表存在记录） + 排除一字板（默认 true）
2. 连板数 ∈ [minContinuousDays, maxContinuousDays]（默认 [1,3]）
3. 所属行业当日 main_inflow 排名 ∈ top topIndustries（默认 10）
4. 流通市值 ∈ [30亿, 200亿]
5. 龙虎榜出现 is_famous_yz=true 且 SUM(net_amount) > 0

**出场 4 类 + 优先级**（最先命中即触发；缺数据安全 HOLD）：
- A. 持有 ≥ holdingDaysLimit (default 3) 自然日 → SELL（最高优先级）
- B. (close - entry_price) / entry_price ≤ stopLossPct (default -7%) → SELL
- C. holdingDays ≥ 1 且当日不在 limit_up 池 → SELL（炸板）
- D. holdingDays ≥ 1 且 (open - prev_close)/prev_close ≥ highOpenSellHalfPct
     (default 5%) 且 !half_exited → SELL_HALF
- E. HOLD

**maxPositions cap 流程**（避免过度持仓）：
- 先算 exit signals → kept positions（HOLD + SELL_HALF）占用槽位
- remainingSlots = maxPositions - kept.length
- BUY 取入场候选游资 top remainingSlots
- 已持仓的股票今天又涨停不重复 BUY（excludeStockCodes 集合）

### Learnings for future iterations
- **DragonHead 是第一个引入"per-position 结构化状态"的组合级策略**。
  MultiFactorAlpha 的 `previousSelection: string[]` 不够用 — exit 规则

  防重复减半。**新组合级策略设计时先列 exit 规则需要的状态**，再决定

- **sell_half 信号类型是 schema diff 的合理后果**。BUY/SELL/HOLD 三态
  撑不起"减仓但保留剩余"的语义；新增 `'sell_half'` 联合分支 + jsdoc 标明

- **Exit 流程必须在 entry 之前算 + 互斥** — 已持仓的股票今天又涨停不应
  双重路径（既 HOLD 又 BUY）。strategy 内部维护 `excludeStockCodes`
  集合传给 evaluateEntries 保证不重 BUY。这条 invariant 测试用例
  `test_exit_held_stock_not_re_bought` 显式守住。
- **出场优先级测试用真实价格 + 真实日期**，不要走"今天人为构造矛盾场景"

  -20% 大亏的真实"双触发"场景，确保线上 holding-day-expiry 永远先于止损

- **`naturalDaysBetween` 故意用自然日不是交易日**。交易日跨周末（周五 +
  3 天 = 周一）会让 holdingDaysLimit=3 实际成为 5 自然日的持仓 — 短线
  龙头战法不应该长这么久。自然日口径是用户期望，文档化在 jsdoc 里防止
  后人误"改进"。
- **DefaultDragonHeadDataSource.loadDailyQuote 的 N+1 陷阱**：初稿用每只
  股票单独 ORDER BY DESC LIMIT 1 拿 prev_close，5 只持仓 = 5 次 round-trip。
  改成一次性查 [as_of - 10 天, as_of] 范围，TS 端按 stock_id 分组挑当日 +
  当日前一条 bar。MomentumFactor 同款 pattern，可以复用 (没抽公共函数是
  因为查询字段不同 + 各自只一个 caller，避免过度抽象)。
- **业务规则 (excludeOneWordBoard=true) 是默认而非强制**。AC 没说一字板
  必须剔除，但实操中一字板抢不到货 → 默认剔除。提供 override 给回测调研
  用 (如想统计"如果能买到一字板"反事实场景)。这种"业务默认 + 留 override"
  比"硬编码剔除"更尊重未来需求。
- **FakeDataSource 的 `state` 字段 nullable Map<>**：让测试用例只需要
  setup 自己关心的子集 (entry 测试不需 dailyQuote, exit 测试不需
  topIndustries)。比"必填全 5 个 Map" 友好得多——25 个测试用例平均
  只 setup 2-3 个 Map。

  `test_exit_hold_kept_consumes_buy_slot` 用了一次让 dataSource 在
  构造后还能 mutate。设计妥协：构造时 spread 一个完整 fixture 太啰嗦；
  允许 mutate 是测试便利性的合理代价 (生产代码绝不会这么用)。

  在 tests/ 目录下能跑（tsconfig 不 include 也行，ts-node --transpile-only
  跳过 typecheck），但**必须放在 backend/tests/ 下**而不是 /tmp，否则

### Learnings for future iterations
- **报告期 vs 公告日不能混淆**。AKShare `stock_yjyg_em` 是按 **报告期**
  检索的（输入 `date='20240930'` 拿 Q3 2024 所有股票的预告），dataframe
  的 `公告日期` 列才是真正的事件日。同样模式的端点：`stock_yjbb_em` (业绩
  报表) / `stock_yjkb_em` (业绩快报) / `stock_zcfz_em` (资产负债表)。
  这类端点的 SyncService 入口应是 `syncReportPeriod` 不是 `syncDate`，
  CLI 应暴露 `--year=YYYY` 一键展开 4 季度。
- **3-tuple PK 是正确选择**。曾考虑用 (announce_date, stock_code) 2-tuple
  覆盖修订 — 但一只股票同一公告日同时披露 Q1+H1 多个报告期是合法场景，
  会丢数据。改成 3-tuple 后：(1) 同 announce_date 同 report_period 的修订
  正确 upsert (`updateOnDuplicate`)；(2) 同 announce_date 不同 report_period
  各成独立行；(3) 不同 announce_date 修订各成独立行（保留修订史）。
- **`is_surprise` 是业务标签留 TS 服务**。曾犹豫"在 Python 里直接计算
  is_surprise" — 但阈值 (50%) / 类型白名单 ([预增,扭亏,续盈]) 都是会
  随策略迭代调整的业务规则；放 Python 意味着每次微调要重启服务（akshare
  helper 是 subprocess）。延续 US-006 famousSeats 的统一切分：Python 是
  dumb fetcher，业务规则留 TS。
- **AKShare 公告日字段格式很多**：可能 pandas Timestamp、datetime、
  "20240715"、"2024-07-15"、"2024/07/15"。Python 端兜底逻辑：用 str()
  + 长度 + 第 5 位字符判断，找不到就 fallback 用 report_period 当公告日
  （至少 PK 唯一不会丢数据）。这一类格式 robust 解析是 AKShare 接入的
  通用问题，下个事件驱动策略可以抄过去。
- **3 个组合级策略对比**：
  - MultiFactorAlpha: 月度调仓 / `previousSelection: string[]` / 静态
    universe (全市场 z_score)
  - DragonHead: 每日触发 / `currentPositions: Position[]` (entry_date,
    entry_price, half_exited) / 事件 universe (当日涨停股)
  - EarningsSurprise: 每日触发但事件稀疏 / `currentPositions: Position[]`
    (entry_date, entry_price, entry_report_period) / 事件 universe (当日
    公告预告股)
  schema 选择基于 exit 规则需要的 per-position state — 多一个少一个都不行。
- **事件驱动 + 多源双确认的 DataSource 接口设计**：4 个 loader 比 1 个
  big-bang `loadAll` 好得多 — 单测可独立 mock 每个数据源，过滤 fail 路径
  能精准定位到"是哪一个数据源拒绝了它"。loadXxx() 命名清晰、签名明确
  (date + codes 或 date + lookbackDays + codes)，FakeDataSource 实现 5
  行 fixture + 30 行实现，整套测试 < 1s 完成。
- **入场过滤顺序：早过滤先做**。最便宜的过滤（in-memory enum 比较）排
  最前，最贵的过滤（北向 lookbackDays 历史回看）排最后。一个完美的
  filter 顺序大约能让 80% 的候选在前两步被剔除，只让最少的股票走到
  Promise.all([loadNorthbound, loadMeta, loadDailyClose])。日志里
  `filtered.fail_*` 各分桶计数给 ops 提供"今日候选池被哪一道关卡剔除
  最多"的直观信号，便于参数调优。
- **`computeIsSurprise` 导出供测试用** — 业务规则用 testable pure
  function 实现 + 单测覆盖所有分支 (50 边界 / null / trim / 非白名单
  类型 / null forecast_type) 是迁移到生产前的保险。每次调整阈值就要
  改测试用例，强迫"业务规则改动 = 阈值常量 + 测试用例同步更新"。
- **`--year=YYYY` CLI 是 cron 友好的便利**。运维场景：cron 每月 1 号跑
  `sync:earnings-forecast --year=$(date +%Y)` 即可覆盖当年 4 季度预告
  的全集（skip-existing 让历史 3 季度跳过、当季增量更新）。比一次只能
  传一个 report_period 友好很多。
- **PR 注意点**：`backend/.gitignore` 不会忽略 worktree 里 `backend/node_modules`
  软链接（gitignore 的 `node_modules/` 是目录模式，对软链接文件不生效）。
  `git add` 前一定 `rm backend/node_modules`，否则 git 会跟踪一个指向
  绝对路径的 symlink 入仓。

## 2026/06/07 - US-014

### What was implemented
回测引擎升级：支持 A 股真实约束（T+1 / 涨跌停 / 停牌 / ST 过滤）+ 真实费率
（commission 万 2.5 + min 5 元 / stamp tax 千 1 卖出单边 / **transfer fee 万 0.1
双边——过户费是第三方回测最常漏算的项**）+ 三种执行价模型（next_open /
same_close / **twap_proxy** 新增）+ 拒单审计 trail（rejected_orders 写入
QuantBacktestResult 新增列）。

**核心模块切分**：

把原本散落在 `QuantBacktestEngine` 里 ~300 LOC 的 A 股规则代码全部抽出到
新模块 `backend/src/quant/backtest/AShareConstraintEngine.ts`（pure、无状态、
无 DB 访问、无副作用），引擎本身收敛回到撮合 / 仓位调度。三个公开方法：

1. **`evaluateOrder(ctx)` → `{ok, reason?, detail?}`**
   单一入口判断"能否成交"：T+1 / 涨跌停 / 停牌 / ST 子串识别 / 流动性门槛。
   `reason` 必须是 `RejectionReason` enum 字面量，下游 `block_reasons` 计数器、
   `RejectedOrder.reason` 字段、UI 图表共享同一原因码词表。判定按"早过滤先做"
   顺序：停牌 → ST → 流动性 → 涨跌停 → T+1，最便宜的检查在最前。
2. **`computeFees(amount, side)` → `FeeBreakdown`**
   返回 `{amount, commission, stamp_tax, transfer_fee, total_cost}`。买入：
   `commission + transfer_fee`；卖出：`commission + transfer_fee + stamp_tax`。
   commission = `max(amount * 0.00025, 5)`；transfer_fee = `amount * 0.00001`；
   stamp_tax = `(side === 'sell') ? amount * 0.001 : 0`。自定义费率走 constructor
   注入。
3. **`executionPrice(bar, side, timing)` → `ExecutionPriceResult`**
   三种 timing：
     - `'next_open'`（默认）：bar.open + 滑点（买高卖低）
     - `'same_close'`：bar.close + 滑点
     - `'twap_proxy'`：`(open+high+low+close)/4` + 滑点 —— 简单 VWAP 代理，
       适合龙头/短线策略（比 next_open 更难"完美捕捉开盘脉冲"）
   动态滑点按 turnover 分段：≤ 0 → ×2，< 30M → ×1.8，< 100M → ×1.25，其他 ×1.0。

### Learnings for future iterations
- **`AShareConstraintEngine` 是 codebase 第一个"pure rule engine"模式**。
  之前所有"业务规则"都嵌在 service / strategy / engine 里。pull 出来的
  收益清晰：(1) 引擎收敛回单一职责（撮合调度），(2) 规则可以零依赖单测，
  (3) 未来 live trading 守护或策略层 self-check 可复用同一份判定逻辑
  （而非再 reimplement）。下一个看到"散落多处的相同业务规则"时套这个
  模式：定 enum + 接口 + pure class，原地 inline 用法替换成 inject。
- **`RejectionReason` enum 优先扩 enum 再用是硬规则**。在 PR 评审时见过
  "为了快速调试加个 free-text reason 后忘了删"——这条会破坏所有下游
  aggregation。eslint 没法捕获这类问题，靠 code review + CLAUDE.md 强提醒。
- **`rejected_orders` audit + `block_reasons` aggregate 并行设计**：起初
  想只保留 aggregate（"反正能算出来"），但回测复盘时用户的真实问题是
  "这只票 06-05 为什么没买到？" —— aggregate 答不了，得 audit 行级数据。
  双写多花 10 行代码但解锁完全不同的产品体验。原则：consumer drives
  storage shape，不要 假设 "存这一份就够了"。
- **`isSTName` 双地点存在是一致性陷阱**。把 strategy 层的实现 verbatim 复制
  到 engine 层是一种"显式 duplication 优于隐式 dependency"的取舍——共享
  一个模块意味着 backtest engine 依赖 strategies 模块，反向打破现有的
  "strategies 用 engine 工具" 单向依赖。CLAUDE.md 显式要求同步两边修改,
  规模再大就把它升级到 `quant/shared/StockNameFilters.ts` 共享模块。
- **`twap_proxy` 用 `(open+high+low+close)/4` 而非真实 VWAP**：A 股没有
  公开的 tick-level VWAP（券商有但要付费），用 4 价均值是"足够好"的代理。
  写到 jsdoc 标明 "proxy"，避免后人误以为是真 VWAP。
- **`过户费` 这个项不能漏**：万 0.1 看着小，但活跃账户一年累计能吃掉
  0.2-0.5% 的收益。互联网券商页面上几乎不显示过户费（藏在"其他费用"），
  策略回测者第一次实盘对账时常发现"账面比回测少 N 千"——大概率就是过户费。
  US-014 强制默认收取，并写入 `transfer_fee_rate` 到 diagnostics，让 metrics
  审计能一眼看到这个口径。
- **`buy_commission` 字段语义扩展**：原本只存 commission，现在改成
  `commission + transfer_fee`（买入侧），因为 sell 时算 pnl 必须把买入侧
  所有费用一起扣掉。如果只存 commission，过户费就被"漏到"sell side 算了,
  虽然总数对但 pnl 归因到买入/卖出阶段不正确。这是看起来 invisible 但
  影响"策略归因 vs 实盘对账"的细节。
- **Mock 策略 `AlwaysBuyOnceStrategy` / `AlwaysSellOnDayThreeStrategy`
  是回测集成测试的关键** —— 真实策略（如 MultiFactorAlpha）信号产出依赖
  数据库 / 因子表，根本无法在测试里精准触发"BUY on day 1, SELL on day 3"
  这种场景。Mock 策略 + `ensureRegistered` helper 让端到端测试有完全可控
  的信号输入。下一个回测集成测试照搬这个模式。

### Learnings for future iterations
- **Express 路由次序陷阱 (US-015 第一坑)**：`/:strategyId` 是 catchall
  param 而非字面量；任何 `/strategies/<sub-resource>/...` 必须在 catchall
  之前注册。这条规则适用于所有 router 文件 — 加新 sub-resource 时
  先 grep `:param` 找到 catchall 位置，再决定 insert 在何处。我加了
  注释 "Must be registered before /:strategyId" 让未来 contributor 不会
  为 "字母序整洁" 而上调位置。
- **service 层 unwrap `{success, data}` 信封**比 "组件层每次 await
  res.data.data" 干净得多。代价：service 函数 throw JS Error 时组件需要
  try/catch（marketService.ts 旧模式直接返回整个信封让组件 if/else）。
  US-015 选 throw + 组件 catch，让 happy path 代码直接拿到 typed payload。
  下一个 service 应当沿用，不要新创 "返回 payload" vs "返回信封" 的
  双标准。
- **factor_scores 表空 = 200 + note，而不是 4xx**：前端用 Empty 占位比
  "弹出 message.error 然后空 Table" 友好；后端响应 shape 多一个 `note`
  字段（前端 service 类型上是 `note?: string`）让 latest-picks 与 preview
  共享同一类型，前端只在 picks 处分支判断。
- **Workspace KPI 条不要用 mock 数据**：MultiFactorAlpha 之前 Statistic
  写 value={0}。换成真实 overview.factors.length / max(universe_size) /
  latest_trade_date 后立刻让用户感知到 "系统是不是真的有数据"。每个
  workspace 在 US-015..US-018 完成后都应该有 ≥3 个真实指标的 KPI 条。
- **避免双重并发 fetch**：FactorWorkspace 装载用 Promise.all（一个
  Spinner），不要每个 tab 切换时再 fetch（会让用户在 tab 之间反复加载）。
  preview 是用户 explicit 触发因此独立 loading。这条规则在
  CLAUDE.md "Multi-tab data fetching pattern" 一节明确写下。
- **响应式因子卡片网格**：xs={24}/sm={12}/lg={8}/xxl={6} 让 8 张卡在
  桌面 (xxl ≥ 1600px) 显示 4×2 网格，超大屏不会过宽空荡，手机端 1 列
  栈叠。比硬编码 `style={{width:300}}` 友好得多。后续 workspace 卡片
  网格统一这个断点。
- **CLAUDE.md 维护 = 1 个文件 + 多个 section** 比每个目录散落更好。
  frontend/src/pages/workspace/CLAUDE.md 现在涵盖 layout 契约 / KPI
  约定 / service 层 / 多 tab fetch 4 大主题；下一个 workspace 实现时
  优先扩这一个文件而不是新建散落 README。
- **Worktree gotcha (still active)**: rm frontend/node_modules + backend/node_modules
  before git add (两个都是软链接污染 git status)。

### Learnings for future iterations

**前端 workspace 大型组件拆分模式**：当 workspace 单个 tab 内容超过 ~150 行时，把它抽成同文件内的子组件（如 `MyStrategiesTab` / `NewBacktestTab` / `CompareTab`），用 props 把 state 透传下去，主组件只做 layout/路由/共享 state。LabWorkspace 这次切了 3 个子组件 + 1 个 helper `CompareChartCard` + 1 个 helper `CompareTableCard`，可读性比 850 行 monolith 强一截。
- **Sub-component 不要 export**：保留 module-private 帮助代码集中。
- **共享 helper（fmtPct/percentTag/statusColor/statusLabel/compactDate）放文件底部** —— 同款 reset/cleanup 模式与 QuantBacktestLab 一致。

**轮询 useEffect 在工作区内的标准模式**：
```ts
useEffect(() => {
  if (!pollingTaskId) return undefined;
  const timer = window.setInterval(async () => {
    const detail = await labService.getBacktestDetail(pollingTaskId);
    const status = detail?.task?.status;
    const list = await labService.listBacktestTasks(50);  // 顺便刷整个列表
    setTasks(list);
    if (status === 'COMPLETED' || status === 'FAILED') {
      setPollingTaskId(null);
      message[status === 'COMPLETED' ? 'success' : 'error'](...);
    }
  }, 3000);
  return () => window.clearInterval(timer);
}, [pollingTaskId]);
```
要点：(1) 在轮询结束时同时刷新 list，否则用户切回"我的策略" tab 看到的还是旧数据；(2) 网络失败时静默吞掉，下一次 tick 自然重试；(3) cleanup 用 `window.clearInterval` 避免 SSR/TS 兼容性吵闹。

**Recharts 多曲线叠加的数据组装**：每条曲线必须用同一个 `data` array，每个 row 是 `{date: 'YYYY-MM-DD', task_5: 12.3, task_8: 9.8, ...}`，然后 N 条 `<Line dataKey="task_N" />`。如果用 N 个不同 `data` array 会导致 X 轴无法对齐。组装时用 `Map<date, row>` 累积，最后 `.sort()` 输出。
- **共享 X 轴 = recharts 的硬性要求**，不要被 "每个 series 独立 data" 的旧 chart.js 习惯误导。

**Antd InputNumber<number> 显式泛型**：当用 `formatter` + `parser` 时，TS 会从 `min`/`max` 字面量类型推断 `value` 是字面量 union（`10000 | 100000000`）而不是 `number`，必须写 `<InputNumber<number> min={...} max={...} parser={...}>` 显式声明，否则 `parser` 返回 number 会报 TS2322。

**Antd Card actions 数组**：`actions={[<A />, <B />]}` 数组里的子元素都要 `key`，**包括外层 Tooltip 包装**。`<Tooltip><a key="x">...</a></Tooltip>` 中 Tooltip 是真正在数组里的元素，需要 `<Tooltip key="x-tooltip">`。eslint 的 react/jsx-key 会精确报错到行号，遇到先看是不是外层 wrapper 漏 key。

**前端 service 文件命名 = `<workspace>Service.ts`**：每个 workspace 配一个 service 文件（factorService / labService / portfolioService / ...）。Service 的导出风格统一：N 个命名 export + 1 个聚合 `<workspace>Service = {...}` 默认 export，与 factorService 完全对齐。

**后端 sub-resource 路由位置**（US-015 lesson 再现）：`/backtests/compare` 必须在 `/backtests/:id` 之前注册，否则 Express 把 "compare" 当成 :id 进去；加注释 `// Must be registered before /backtests/:id` 防未来排序。

**回测对比 API 同时返回两种视图**：一个是"按 task 维度的列表"（前端画曲线/任务概览），一个是"按策略 × 任务的二维 cell 表"（前端画对比矩阵）。在 service 一次性算好两份比让前端组合更省事 —— SQL 已经一次拉全所有 Result，重新走一遍 `flatMap` 几乎免费。前端组装这种二维 cell 表本身写起来就别扭（不像 service 端直接 `Map<strategy_key, Cell[]>`），后端预聚合 = 前端代码更线性。

**`metrics_json.turnover_rate` fallback chain**：换手率不是 QuantBacktestResult 的顶层列，藏在 `metrics_json` 里，且历史代码两个位置都写过（`metrics_json.turnover_rate` 和 `metrics_json.execution_diagnostics.turnover_rate`），所以 service 端用 `??` 链 fallback 两个位置 + 默认 0；前端只读这一个字段。

### Learnings for future iterations
- **JSONB 列 mutate 后必须 `model.changed('field', true)`** — 这是 Sequelize
  的 dirty-check 在 JSONB 列上的边角行为；如果 in-place mutate 数组 (push /
  splice) 或者 reassign 整个数组，模型实例的 `_changed` set 都不会
  自动包含这个字段，UPDATE SQL 就不发。`appendNote` 用 `journal.user_notes
  = [...existing, note]` (reassign) + `journal.changed('user_notes', true)`
  双保险。下一个 JSONB 列写入的 endpoint 直接抄这个模式。
- **"懒建档" 模式 (Lazy materialization)** — `POST /journals/:date/notes`
  如果该日期没记录会自动 create 一行 placeholder。这种"用户的写操作先于
  AI 生成数据存在"的模式适用于任何"主数据由 AI 生成 + 用户补充"的领域：
  US-087 (AI 复盘日记自动生成) / US-077 (RiskAlert 备注) 等都可以套
  这个模式。关键判断：placeholder 字段要明确标识 (mood='未生成')，让前端
  能区分 "AI 已生成 + 用户追加" vs "纯用户手记"。
- **discriminator union 扩展 vs 加 facade 方法 — 严格守住 7 个**。
  原本想给 PaperTradingFacade 加第 8 个方法 `setStopLoss`，被
  CLAUDE.md 显式规则拦下 (US-003 留下的硬约束)。扩 `ApplyAutomationAction`
  联合类型 + 一个 case 等价但保持 facade public surface 不膨胀。**未来给
  facade 加新写操作: 先看 7 个 method 哪个语义最近, 再扩它的 action 联合类型**。
- **Inline 编辑 pattern 不用 antd Table 自带 editable** — antd 的
  `record.editable` 配合 EditableContext 是 form-driven 模式，把表单
  state 和 cell render 强耦合，async save (PUT 请求 + 错误重试 + 保留
  编辑态) 难协调。改用 "hoist editingPositionId + editingValue 到 tab
  级 + cell render 分支" 模式：所有状态在 React 标准受控组件里，async
  save → keep edit row open on error 等需求 1-2 行代码搞定。
- **Popconfirm + danger button + 行级 loading state** — 一键平仓是
  destructive 操作，必须 confirm。antd Popconfirm 比自定义 Modal 更
  inline-friendly + 更 accessible。`closingSymbol: string | null` 状态
  隔离让 loading spinner 只显示在执行的行，其他行不被锁。成功后触发整体
  refresh (而非 optimistic patch single row) — 平仓影响 cash + total_value
  + positions[] + trades[]，不能只 patch 单字段。
- **Recharts 多曲线必须共享同一 data array** (US-016 已发现，US-017 复用)。
  组装时用 `Map<date, value>` 索引基准价格，map 我的 snapshot 到 `{date,
  my, benchmark}` 三元组；`connectNulls` 处理节假日断线。**不要**给两个
  Line 各自传不同 data array (那是 chart.js 旧模式，recharts X 轴会对不齐)。
- **基准数据按窗口动态 fetch** — 不在 mount 时 eager fetch 全市场指数 (用户
  可能根本不切到 资金曲线 tab，纯浪费 round-trip)。切换 Segmented window 时
  `useEffect([sliced])` 触发 fetch — sliced 由 windowKey 派生，依赖链清晰。
- **`getJournalDetail` 404 → null** 比 throw 更友好 — "该日期还没有日记"
  是预期场景而非错误，UI 用 Empty 占位 + 提示 "可追加手记建档" 是正确
  reaction。service 层做 axios 404 拦截避免 component 写 try/catch。
- **共享 helpers (pnlColor / computeSharpeRatio / annualizeReturnPct) 留
  workspace 内**：这些 helper 仅 PortfolioWorkspace 用。如果未来 EquityCurve
  抽出到 TodayWorkspace 也需要，再升级到 `frontend/src/utils/portfolio.ts`。
  现在过早抽象会让 import 路径混乱。
- **`所属策略` 列暂用 '手动' Tag 占位**: 真正的 strategy → trade 归属
  需要 join QuantSignal 表 (PaperTradingAttribution 已经做了，但 cost
  是每次 portfolio fetch 都额外 N 次 round-trip)。US-088 之后会有专门
  endpoint 一次性返回 positions + strategy_origin，那时再加进来。
- **Worktree gotcha (still active)**: before `git add`, 删 `frontend/node_modules`
  + `backend/node_modules` symlink (两个都污染 git status；gitignore 的
  `node_modules/` 是目录模式，对软链接文件不生效)。

### Learnings for future iterations

#### 后端 service 聚合 — 并发 + per-block error fallback 是新工作区的模板
- **`Promise.all` + `.catch(e => fallbackBlock)`** 是新工作区聚合 service 的标准模板。每个 block 自带 `error?: string` 字段，前端按需在 Card 顶部显示 `<Alert>`。这样一个数据源缺失（factor_scores 没跑过 / EarningsForecast 表空）不会把整页打挂。Pattern 直接复用到 US-019..US-023 的新策略接入今日页：每加一个策略 = 加一个 `compute<Strategy>Block` 方法 + `Promise.all` 一项 + UI 一列 Card。
- **遗留 service 共存策略**：US-018 没动 850 行的 `TodayCommandCenterService`，而是新建 `TodaySignalsService` 服务新 endpoint `/api/today/signals`。`/api/today/command-center` 旧 endpoint 仍由旧 service 服务（可能被某些遗留页面或 cron 调用）。后续 US-099+ 收敛旧 service 时再合并；目前并存优先保持新功能干净。
- **`paperTradingFacade.placeOrder` 是规范的下单入口** — US-018 的一键应用功能套用 facade，没绕开（如果绕开 → 容易跟 risk profile / automation 等内部 hook 不一致）。新增任何"自动下单"功能（一键应用 / 自动调仓 / strategy 触发）都应该过 facade.placeOrder，不要直连 PaperTradingPosition.create。

#### 前端 workspace pattern — 3 列卡片 + 一键操作 + 跳转
- **3 列 + Card.error 模板** — 任何"对比多个 source/strategy/dimension" 的页都可以套这个布局：每个 Card 用 `<Space size={24}>` 三件套 mini-KPI + 主 Table + 错误 Alert。MultiFactor / DragonHead / EarningsSurprise 三个 Card 的代码可读为同一模板的 3 个 instance；未来 US-019..US-023 新策略加 Card 就照抄一遍。
- **一键操作 → Popconfirm + Modal + navigate** — Popconfirm 处理 "确认要下 N 单吗" 的二次确认（用户最容易误触）；下单成功后弹 Modal 展示明细（让用户看到每笔下单结果，包括 placed/skipped/failed），2 秒延时 + `useNavigate()` 跳转目标页（避免用户被瞬间转走来不及看结果）。这个组合可复用到 US-019 北向加仓策略的"一键跟单"、US-022 高分红策略的"一键建仓"等场景。
- **`useNavigate` from react-router-dom** 在工作区内部跳转 — 之前没有 workspace 用过 react-router 的 navigate hook (US-015..US-017 都是单页内部 tab 切换)。US-018 是第一个用 `useNavigate('/workspace/portfolio')` 做跨工作区跳转的页。**确认 react-router v6 模式：直接 import `{ useNavigate }` 即可，不需要 wrapped Router context**。
- **`pnlColor` 函数返回 `undefined as unknown as string`** 处理"零值不上色"场景 — antd `Statistic.valueStyle.color` 类型要求 `string`，但 `undefined` 才能让它走默认色（不是黑也不是灰）。这个 type-cast hack 是 antd v5 valueStyle 设计的妥协，US-017 PortfolioWorkspace 已有同样写法，US-018 沿用。

#### 数据准备状态 — 三策略需要的表（早期会大量 error/empty 是正常）
- MultiFactorAlpha 需要 `factor_scores` 表有数据 → `npm run compute:factors -- --date=YYYY-MM-DD`
- DragonHeadMomentum 需要 `limit_up_stocks` + `industry_flows` + `dragon_tiger_boards` → US-007/008/006 各自 sync 脚本
- EarningsSurprise 需要 `earnings_forecasts`（有 is_surprise=true 的行）+ `northbound_holdings` → US-013/005 各自 sync 脚本
- 当任一表为空时，对应 block 显示 `error: "..."` 而不是空白 — 用户看到的是"缺数据，请运行 X 脚本"而不是"功能坏了"。

Added **NorthboundFollowStrategy** (4th 组合级 strategy) — a 跟随类 strategy
that scans every trading day for stocks where 北向资金 has been accumulating
over the prior 5 trading days, then exits when 北向 reverses, the position
hits stop-loss, or the 30-day holding period expires.

**Design (vs the 3 prior 组合级 strategies)**:

| 维度 | MultiFactorAlpha (US-011) | DragonHead (US-012) | EarningsSurprise (US-013) | NorthboundFollow (US-019) |
|------|--------------------------|---------------------|---------------------------|--------------------------|
| 触发节奏 | 月度调仓 | 每日 (事件驱动) | 公告日 (事件驱动) | 每日 (全市场扫描) |
| Universe 构造 | factor_scores 全市场 | LimitUpStock 当日涨停 | EarningsForecast 当日预告 | NorthboundHolding 有连续数据全市场 |
| Exit 复用 entry 数据源 | n/a (月度) | 否 (close + limit_up) | 否 (close + holding 天数) | 是 (entry & exit 同读 ratioSnapshots) |
| Position schema | string[] | Position[] (含 half_exited) | Position[] (含 report_period) | Position[] (含 entry_ratio) |
| 出场看反向信号 | 否 | 否 (炸板≠北向减仓) | 否 | **是** (北向减仓 -0.3pp → SELL) |

跟随类策略和事件驱动策略的核心差异：跟随类的 alpha 是"和聪明钱同向"，
所以**反向信号必须做出场线**——否则就只剩"持有期到期"+"止损"两条
被动出场，本质失去 alpha。

### Learnings for future iterations

#### 设计层 (会反复出现)
- **跟随类策略的 DataSource 接口不要让 caller 传 universe**:
  跟随类的候选池就是"有近 N+1 天连续数据的全市场股票"，没有更上游的过滤
  源。如果 loader 强制要求 `stockCodes: string[]`，caller 反而要先发一遍
  Sequelize 查询去拿 universe，等于重复查询。正确签名是
  `loadCandidateRatioDeltas(asOfDate, lookbackDays): Promise<Map>`。
- **同源数据 entry + exit 复用的边界 = 主流程层**：US-019 的
  ratioSnapshots 在主 `generateSignals` 里拉一次，然后传递给
  `evaluateEntries` 和 `evaluateExits`。**不要**在两个 evaluate 里各自
  `await this.dataSource.loadX(...)` —— 同样的 SQL 跑两次是 wasted IO，
  也会导致两侧"看到的快照"理论上不一致 (如果中间有别的 process 写入)。
- **跟随类策略必须有"反向信号出场线"**：US-019 的优先级 A→B→C 把"持有
  期到期 + 止损"放在 "北向减仓" 前面，让硬约束优先；"北向短期减仓" 是
  软信号容易误判，但**少了它整个策略就退化为单纯的均值回归 + 止损**，
  alpha 来源不再是"跟随聪明钱"。这条 guard 是跟随策略的命脉。
- **boundary 测试要写 `≥` vs `>`**: US-019 入场用 `ratio_delta >=
  minIncreasePct`（inclusive），但 `current_ratio > minCurrentRatio`
  (exclusive)。这种细微差异 AC 里没明确说，但单测写 boundary case 强迫
  作者明确选择——`>= minIncreasePct` 更宽容、容易触发；
  `> minCurrentRatio` 更严格、避免"刚到 1.0% 的微仓"被算成"已建仓"。
  Test 28 验证了 `=` 边界入选。
- **Position 字段加 entry_ratio 是为了 debug 不是为了出场逻辑**：
  US-019 出场看 `ratioSnapshots[code].ratio_delta` (5 日累计差)，不看
  `current_ratio - entry_ratio`。但 entry_ratio 保留在 Position 里方便
  复盘——"我进的时候北向才 1.5%，现在已经追到 3.0% 了" 这种洞察对调参
  很有用。判据仍是 "调仓规则需要哪些 per-position state 就放哪些字段"，
  entry_ratio 是 debug-only 字段而非 exit-driving 字段，所以 schema
  允许它 optional (注释清楚)。

#### 工具层 (本环境特定)
- **worktree 下需要 backend node_modules 软链**：执行 `cd backend && ln
  -sfn /Users/bytedance/go/src/github.com/bruinxz/stocks/backend/node_modules
  node_modules` 再跑 tsc / ts-node / eslint。这条已在 Codebase Patterns
  里，再次确认。提交前不需要 rm —— `backend/.gitignore` 的
  `node_modules/` pattern 会 silently 忽略软链 (与 frontend 不同 — frontend
  的 .gitignore 需要 explicit 排除软链)。
- **eslint --fix 改了文件，必须**重新 typecheck + 重新跑测试再 commit。
  prettier 自动格式化可能把 long if-else 拆行，绝大多数情况不破坏逻辑，
  但偶尔会触发 unused-var 等次生错误。
- **测试运行命令模式** (与 US-011..US-013 一致): `cd backend && npx ts-node
  --transpile-only tests/strategies/<Strategy>.test.ts`。`--transpile-only`
  跳过类型检查（tsc 那一步已经做过），加速 5-10×。运行时 < 1s 是 fake
  DataSource + 无 DB 的好处，集成测试请另开目录。

### Codebase Patterns (新增)
- **跟随类策略 DataSource 签名**：`loadCandidateXxx(asOfDate, params)`
  返回 `Map<stock_code, snapshot>` 一次性给出全市场快照——不要让 caller
  传 stockCodes 列表。同源数据用一份在主流程，传递给 entry/exit 评估方法
  做参数，**不要**在 evaluate 内部重复 fetch。
- **组合级策略对比表已扩到 4 个 (US-011/012/013/019)**: 触发节奏/Universe
  构造/Exit 复用 entry/Position schema/反向信号出场线 — 5 个维度。新加
  组合级策略前先回看这张表，避免"为了用同样模板"而设计错误的 DataSource
  接口形态。
